## 一、版本定位

当前平台已经支持任务执行、运行记录、执行可靠性和部署交付，但用户仍然很难回答一个关键问题：

> AI 到底改了哪些代码，这些代码能不能放心上线？

完整 diff 对普通用户信息过载，对专业开发人员也很难在几千行变更中快速判断风险。V1.0.6 不再增加新的任务类型或执行器，而是新增一条“AI 变更审阅”闭环：

```text
任务执行完成
  → 生成结构化变更快照
  → 按意图和风险拆分审阅单元
  → AI 预审并给出有行号证据的发现
  → 用户快速验收关键变更
  → 通过、要求修改或驳回
  → 通过后才能部署
```

## 三、产品原则

### 1. 不新增一级菜单

审阅入口只放在：

- 任务详情。
- 执行控制塔中的已完成任务。
- 交付前的发布检查。

### 2. 先看变更意图，再看 diff

默认首屏不展示完整代码 diff，先展示：

- AI 完成了什么。
- 修改了哪些行为。
- 哪些地方风险最高。
- 有什么测试和运行证据。
- 用户下一步应该做什么。

### 3. 人是最终验收者

AI 可以做预审、分类和解释，但不能把“AI 认为没问题”等同于人工验收。高风险变更必须由人确认。

### 4. 审阅必须绑定具体代码事实

每条摘要、风险和问题都必须绑定：

- 变更快照。
- 文件。
- 行号或 hunk。
- 对应任务或验收标准。

没有代码证据的 AI 结论只能作为建议，不能成为验收依据。

### 5. 代码变化后旧审阅自动失效

审阅结果必须绑定 base commit、head commit 和 diff 哈希。只要代码再次变化，旧审阅结论不能继续用于发布。

## 四、本版本不做

- 不做完整 Git PR 平台。
- 不替代 GitHub、GitLab 的代码托管和评论能力。
- 不要求用户逐行阅读所有改动。
- 不允许 AI 自动批准数据库、权限、部署或密钥相关高风险变更。
- 不做代码所有权、团队审批链和复杂 RBAC。
- 不做静态分析平台的完整替代。

## 五、版本成功指标

| 指标 | 目标方向 |
|---|---|
| 用户理解本次变更所需时间 | 从分钟级降到 3 分钟以内 |
| 用户实际查看高风险 diff 的比例 | 持续提升 |
| 未审阅直接部署的任务比例 | 显著下降 |
| AI 审阅误报率 | 可控并可反馈修正 |
| 上线后回滚或紧急修复率 | 持续下降 |
| 审阅后要求 AI 修改的闭环成功率 | 持续提升 |

## 六、开发交付顺序

1. 先建立 ReviewSnapshot、ChangeUnit、Finding、ReviewDecision 的数据事实。
2. 再实现 AI 预审、风险分组和证据关联。
3. 然后实现任务详情中的审阅 UI。
4. 最后接入发布门禁和审计。

## 七、明确不做成什么

- 不是把所有 diff 堆在页面上的“代码查看器”。
- 不是根据关键词随便标红的风险扫描器。
- 不是 AI 说一句“审查通过”就自动发布。
- 不是新的顶级“代码中心”菜单。
