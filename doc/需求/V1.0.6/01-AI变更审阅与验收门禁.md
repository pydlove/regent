| 项目 | 内容 |
|---|---|
| 需求编号 | REG-V106-REV |
| 优先级 | P0 |
| 文档版本 | v1.0 |
| 状态 | 待产品评审 |

| 适用版本 | Regent_V1.0.6_R100B021 |

## 一、背景与问题

AI 执行任务的速度越来越快，但用户对代码的感知没有同步提升：

1. 任务结束后只看到“完成”，不知道具体改了什么。
2. 文件多、代码长，完整 diff 难以阅读。
3. AI 的说明可能与实际代码不一致。
4. 用户不知道哪些改动是核心逻辑，哪些是格式化或生成代码。
5. 测试通过不等于业务行为正确。
6. 代码审阅与部署流程割裂，用户可能没看代码就直接发布。
7. 用户提出修改意见后，需要重新找到对应会话和上下文。

核心问题不是“没有 diff”，而是：

> 用户缺少一套能快速理解变更、抓住风险、验证证据并做验收决策的工作流。

## 二、目标

### 1. 业务目标

- 降低 AI 代码的审阅门槛。
- 缩短从任务完成到人工验收的时间。
- 提高高风险变更的人工审查覆盖率。
- 让部署和代码变更建立可追溯关系。
- 让用户的审阅意见直接回到原任务会话。

### 2. 用户体验目标

- 用户打开任务后 3 分钟内理解本次变更。
- 默认只看关键变更，完整 diff 按需展开。
- 高风险代码不会被格式化或生成文件淹没。
- 用户能一眼看到测试、日志、截图和运行证据。
- 用户能对某个变更点要求 AI 解释或修改。
- 未审阅或审阅已失效的任务不能进入正式发布。

### 3. 非目标

- 不实现完整 PR 系统。
- 不做逐行强制审批。
- 不承诺 AI 预审可以发现所有缺陷。
- 不自动批准高风险变更。
- 不建立新的代码托管系统。

## 三、目标用户与场景

### 1. 产品经理

不熟悉代码，但需要确认这次 AI 是否真的完成了业务需求。

### 2. 开发人员

需要快速查看核心逻辑、接口、数据库和潜在回归风险。

### 3. 测试人员

需要知道哪些行为发生变化，以及有哪些测试和运行证据。

### 4. 项目负责人

需要在部署前决定是否接受本次变更，或者要求 AI 继续修改。

## 四、核心产品模型

### 1. 审阅快照 ReviewSnapshot

一次审阅对应一组固定的代码事实：

- 任务 ID。
- 执行记录 ID。
- 项目 ID。
- base commit。
- head commit。
- diff 哈希。
- 变更文件数量。
- 增删行数。
- 生成时间。

代码一旦变化，旧快照仍然保留用于审计，但状态变为“已过期”。

### 2. 变更单元 ChangeUnit

把 diff 按业务意图而不是文件列表分组。

每个变更单元包含：

- 业务标题。
- 修改原因。
- 风险等级。
- 所属模块。
- 文件列表。
- 关键 hunk。
- 关联需求或验收标准。
- 验证证据。

示例：

```text
核心行为变更：任务认领并发控制
风险：高
文件：AgentRunService.java、TaskRun.java、TaskMapper.xml
原因：同一任务只允许一条 RUNNING 执行记录
证据：并发单测、数据库唯一约束测试
```

### 3. 审阅发现 ReviewFinding

AI 或规则产生的具体问题：

- 严重级别。
- 问题描述。
- 影响范围。
- 文件。
- 行号或 hunk。
- 证据。
- 建议操作。
- 状态：待确认、属实、误报、已修复。

### 4. 验证证据 Evidence

- 单元测试结果。
- 集成测试结果。
- 构建结果。
- 运行命令和退出码。
- 关键日志。
- UI 修改前后截图。
- 接口请求与响应示例。
- 部署预检结果。

### 5. 验收结论 ReviewDecision

- 通过。
- 要求修改。
- 驳回。

审阅结论必须记录操作者、时间、快照和意见。

## 五、审阅状态

| 状态 | 含义 |
|---|---|
| 未生成 | 任务完成后尚未生成审阅快照 |
| 待审阅 | 快照已生成，等待用户查看 |
| 审阅中 | 用户已开始查看或处理意见 |
| 待修改 | 用户要求 AI 修改，任务重新执行 |
| 已通过 | 当前快照被人工接受 |
| 已驳回 | 当前变更不允许进入部署 |
| 已过期 | 代码已变化，旧结论不能用于发布 |

## 六、功能需求

### REV-01 生成审阅快照

任务执行成功后自动生成审阅快照。

要求：

- 读取任务开始前的 base commit 和当前 head commit。
- 排除二进制文件正文，但保留文件元信息。
- 计算稳定 diff 哈希。
- 支持没有 Git 仓库的项目降级为文件变更清单。
- 快照生成不应阻塞任务收场。

验收：

- 任务完成后能看到审阅入口。
- 快照包含 commit、文件数和增删行数。
- 同一快照重复打开内容一致。

### REV-02 按意图分组变更

AI 根据任务目标、验收标准和 diff 生成变更单元。

要求：

- 不按文件树机械罗列。
- 同类改动归入一个单元。
- 生成文件、锁文件、格式化文件单独归组。
- 每个单元说明“为什么改”和“影响什么”。
- 无法确认意图时明确标记，不得猜测。

验收：

- 用户先看到 3 到 8 个主要审阅单元，而不是全部文件。
- 生成代码和依赖锁文件默认折叠。
- 点击单元可以查看对应 diff。

### REV-03 风险识别与优先级排序

系统根据规则和 AI 分析标记风险。

高风险至少包括：

- 数据库迁移。
- 权限和认证。
- 支付、密钥、证书。
- 部署脚本和服务器操作。
- 公共接口和数据契约。
- 跨模块核心行为。
- 删除数据或不可逆操作。

中风险至少包括：

- 核心业务条件分支。
- 错误处理。
- 新增依赖。
- 大量文件重命名。

低风险至少包括：

- 文案。
- 注释。
- 测试补充。
- 纯格式化。

验收：

- 高风险单元默认展开。
- 低风险单元默认折叠。
- 用户能筛选“只看高风险”。

### REV-04 展示验证证据

每个变更单元关联可用的验证证据。

要求：

- 测试结果必须显示命令、结果和关联测试。
- UI 变更尽量提供截图或可点击预览。
- 接口变更提供请求响应示例。
- 数据库变更提供表、字段和迁移风险。
- 不把“没有证据”显示成“已验证”。

验收：

- 用户能区分通过、失败、未执行和不可验证。
- 证据可以打开到完整运行记录。

### REV-05 AI 预审发现

AI 在用户验收前完成一次结构化预审。

要求：

- 发现问题必须关联具体文件和行号。
- 按阻断、严重、一般、提示排序。
- 明确哪些问题已修复，哪些仍未处理。
- 支持用户标记误报。
- 预审结论不能直接等于人工验收通过。

验收：

- 每条发现可以定位到代码。
- 用户关闭页面后，处理状态不丢失。
- AI 不得输出没有代码位置的核心阻断问题。

### REV-06 解释和修改闭环

用户可以针对变更单元或具体 hunk 发起：

- 解释这段为什么改。
- 这里有没有回归风险。
- 补一个测试。
- 按我的意见修改。
- 只修改这个单元。

操作必须回到原任务的 Codex 会话上下文。

验收：

- 用户意见会生成新的执行输入。
- 新执行不会丢失原任务背景。
- 修改完成后生成新的审阅快照。

### REV-07 审阅进度和结论

页面展示：

- 必须查看的单元数量。
- 已查看数量。
- 未处理发现数量。
- 当前是否满足通过条件。

结论动作：

- 通过当前快照。
- 要求修改。
- 驳回本次变更。

验收：

- 存在未处理的阻断问题时不能通过。
- 通过后记录操作者和时间。
- 代码再次变化后状态自动变为已过期。

### REV-08 部署门禁

部署前检查任务是否存在有效审阅结论。

规则：

- 高风险任务必须人工通过。
- 中风险任务至少确认所有高风险单元和阻断问题。
- 低风险任务可按项目策略自动验收，但必须保留证据。
- 审阅已过期时禁止正式部署。

验收：

- 未审阅任务执行正式部署时显示明确阻断原因。
- 从审阅页面可以直接继续到部署。
- 部署记录关联审阅快照。

### REV-09 审阅审计

记录：

- 审阅人。
- 审阅时间。
- 查看过的单元。
- 误报标记。
- 要求修改的意见。
- 最终结论。
- 是否作为部署依据。

## 七、页面与交互

### 1. 任务详情新增“变更审阅”页签

首屏结构：

1. 本次任务完成摘要。
2. 风险分布。
3. 必须查看的变更单元。
4. AI 预审发现。
5. 验证证据。
6. 通过、要求修改、驳回。

### 2. 不默认展示完整 diff

完整 diff 放在每个变更单元内部。

提供三种视图：

- 摘要视图。
- 关键 hunk 视图。
- 完整 diff。

### 3. 审阅单元卡片

每张卡片展示：

- 标题。
- 风险。
- 修改文件数。
- 业务说明。
- 验证状态。
- 问题数量。
- 展开/已查看状态。

不使用同等大小的大卡片堆满页面，按风险和状态形成紧凑列表。

### 4. 代码上下文

- 行号固定。
- 支持语法高亮。
- 默认只展示修改行及必要上下文。
- 可以展开完整文件。
- 文件、hunk 和发现之间可以互相跳转。

## 八、业务规则

1. 审阅结论必须绑定具体快照，不能只绑定任务。
2. 代码再次变化后，旧审阅立即过期。
3. AI 预审通过不视为人工通过。
4. 高风险规则命中必须人工确认。
5. 误报标记不删除原文，只改变状态和计数。
6. 审阅意见进入原任务会话，不能另开无上下文的任务。
7. 生成文件、锁文件和二进制文件默认不进入人工主审队列。
8. 所有风险结论必须能从代码或规则中找到证据。

## 九、非功能要求

- 1 万行以内 diff 的首屏摘要加载控制在 3 秒内。
- 超大 diff 使用分页或按单元懒加载。
- 原始 diff 不改写，只做展示和归类。
- AI 审阅失败不能阻塞任务完成和运行记录查看。
- 审阅状态和快照必须持久化。
- 敏感文件、密钥和 Token 内容不得进入审阅摘要。

## 十、验收场景

### 场景 1：AI 修改了大量文件

**Given** 任务修改了 80 个文件，其中 50 个是生成文件  
**When** 用户打开变更审阅  
**Then** 首屏只展示 5 到 8 个主要审阅单元  
**And** 生成文件折叠为单独分组  
**And** 高风险核心逻辑默认展开

### 场景 2：AI 报告完成但代码有风险

**Given** AI 认为任务完成  
**When** 预审发现数据库迁移可能导致历史数据丢失  
**Then** 页面标为阻断问题并关联迁移脚本行号  
**And** 用户不能直接通过审阅

### 场景 3：要求 AI 修改

**Given** 用户在某段代码添加审阅意见  
**When** 点击“按意见修改”  
**Then** 原任务会话收到带代码位置和意见的新执行输入  
**And** 修改完成后生成新快照  
**And** 旧快照标记为已过期

### 场景 4：未审阅直接部署

**Given** 高风险任务没有有效审阅结论  
**When** 用户发起正式部署  
**Then** 平台阻断并提示先完成变更审阅  
**And** 提供直接进入审阅页面的入口

### 场景 5：代码在审阅后变化

**Given** 用户已通过某个审阅快照  
**When** AI 又修改了代码  
**Then** 旧审阅状态变为已过期  
**And** 部署门禁重新阻断

## 十一、技术边界

- Git diff 读取通过端口实现，核心域不直接调用 Git 命令。
- AI 预审通过执行器端口或独立 reviewer 适配器实现。
- 审阅快照、发现和结论必须经过领域模型和仓储，不允许只在页面内存中保存。
- 对外接口只返回 DTO，不暴露领域对象。
- 审阅结果必须绑定 diff 哈希，不能只绑定任务号。
- 现有任务状态机不直接新增“已审阅”业务状态，审阅状态独立管理。
- 已有 V 脚本不得修改，新增表结构必须使用新的 Flyway 迁移。

## 十二、MVP 交付范围

### 必须交付

- 审阅快照。
- 变更单元和风险分组。
- AI 关键发现与行号定位。
- 测试、日志、截图等证据入口。
- 通过、要求修改、驳回。
- 发布门禁。
- 快照变更后的失效机制。

### 可以延后

- 行内评论和完整 PR 式协作。
- 多审阅人。
- 审阅规则可视化编辑。
- 代码所有权和团队路由。
- 自动修复所有误报。

## 十三、成功指标

| 指标 | 衡量方式 |
|---|---|
| 首轮审阅完成时间 | 从打开审阅到通过或要求修改 |
| 高风险代码查看率 | 必看单元中实际展开的比例 |
| 审阅后部署率 | 正式部署前存在有效结论的比例 |
| 审阅失效拦截率 | 代码变化后旧结论被阻断的次数 |
| AI 预审误报率 | 被用户标记误报的发现比例 |
| 修改闭环成功率 | 要求修改后再次通过审阅的比例 |
| 上线后回滚率 | 已审阅和未审阅任务的发布后回滚差异 |

## 十四、风险与待确认项

| 风险 | 影响 | 建议 |
|---|---|---|
| AI 摘要与代码事实不一致 | 用户被误导 | 摘要必须绑定 diff/hunk，无证据不生成结论 |
| 审阅界面过于复杂 | 用户仍不愿看 | 默认摘要和风险优先，完整 diff 折叠 |
| 超大 diff 性能差 | 页面卡顿 | 按单元懒加载和分页 |
| 风险规则误报 | 审阅疲劳 | 规则可解释，允许标记误报并反馈 |
| 审阅成为发布瓶颈 | 交付变慢 | 低风险任务支持项目策略自动验收 |
