## 一、结论

本版本新增独立支撑上下文 `review`，不修改任务状态机，不把“已审阅”塞进 `TaskStatus`。

核心设计结论：

1. `ReviewSnapshot` 是审阅聚合根，固定一次任务尝试的 base commit、head commit、diff 哈希、
   文件统计与完整 diff 原文。
2. `ChangeUnit`、`ReviewFinding`、`ReviewEvidence` 是 `ReviewSnapshot` 内的实体。
   它们不能脱离快照单独成立，统一由 `ReviewSnapshotRepository` 取聚合来改。
3. `ReviewDecision` 是独立聚合，只保存快照 ID、结论、操作者、意见和时间，作为不可变审计事实。
4. 审阅状态独立于任务状态。任务成功仍先按现有流程进入 `DONE`，审阅生成是收场后的旁路动作，
   失败不能回滚任务，也不能阻塞运行记录查看。
5. 部署门禁不信任页面参数。正式部署请求必须带 `taskId`，应用服务读取该任务当前有效快照，
   重新计算当前 diff 哈希并与快照比对，一致且已人工通过才放行。
6. 外部 Git diff 与 AI 预审分别通过 `ReviewDiffReader`、`ReviewAnalyzer` 端口访问，
   实现全部放在 `regent-infrastructure`，核心域不出现 Git、ProcessBuilder、JSONL 或 HTTP 类型。
7. 审阅入口嵌入任务详情和执行控制塔，不新增一级菜单。

## 二、当前代码事实与约束

### 2.1 可复用能力

- `RunSettlementService.finishAttempt` 是内部执行与外部执行者共用的统一收场入口，
  审阅快照生成必须挂在它成功收场之后，保证两条执行链路行为一致。
- `TaskRun.changedFiles` 已保存执行器上报的变更文件，可作为文件清单交叉校验，
  但不能替代 Git diff 事实。
- `TestCaseRunRepository.findByTask` 能提供任务完成后的测试命令、状态、退出码和摘要。
- `ProjectProfile.path` 能提供项目工作区绝对路径。
- 账户隔离通过项目归属校验完成；审阅接口必须先校验任务或部署所属项目属于当前用户。
- 现有 Flyway 最大版本为 `V41`，本版本从 `V42` 开始追加，不修改任何历史脚本。

### 2.2 当前缺口

- `TaskRun` 没有记录执行开始时的 base ref，无法可靠回答“这次任务改了哪些代码”。
- 现有部署执行不携带任务上下文，无法判断“这次要部署的代码是否经过审阅”。
- 现有运行记录只有摘要和事件流，不是结构化审阅事实。

## 三、领域边界

### 3.1 ReviewSnapshot

职责：

- 绑定一次任务与一次执行记录。
- 固定代码事实：base commit、head commit、diff 哈希、文件数、增删行数、完整 diff。
- 维护审阅生命周期：待审阅、审阅中、待修改、已通过、已驳回、已过期。
- 维护其内部实体集合，并作为通过条件的唯一判断入口。

不负责：

- 修改任务状态。
- 执行 Codex 或 Git 命令。
- 发送通知。
- 直接触发部署。

状态迁移只能走领域方法：

```text
WAITING_REVIEW ──begin──▶ IN_REVIEW
WAITING_REVIEW / IN_REVIEW ──requestChanges──▶ CHANGES_REQUESTED
WAITING_REVIEW / IN_REVIEW ──approve──▶ APPROVED
WAITING_REVIEW / IN_REVIEW ──reject──▶ REJECTED
任意未终态 ──expire──▶ EXPIRED
```

通过守卫：

- 至少存在一个人工确认动作，AI 预审结论不能调用 `approve`。
- 不得存在状态不是 `FALSE_POSITIVE`、`FIXED` 的 `BLOCKER` 发现。
- 所有必需查看的高风险单元必须已标记查看。
- 快照必须处于有效状态，已过期快照不能再次通过。

### 3.2 ChangeUnit

定位：`ReviewSnapshot` 内实体。

职责：

- 按业务意图聚合文件与关键 hunk。
- 保存标题、修改原因、所属模块、风险等级、默认展开策略和查看状态。
- 区分业务变更、生成代码、依赖锁文件、纯格式化、二进制文件。

关键约束：

- 文件路径和 hunk 必须属于本快照。
- 高风险单元默认必须查看；低风险和生成类单元默认折叠。
- 无法确认业务意图时使用“尚未确认意图”标题，不猜测。

### 3.3 ReviewFinding

定位：`ReviewSnapshot` 内实体。

职责：

- 保存严重级别、描述、影响、文件、行号或 hunk、建议动作和证据。
- 状态支持待确认、属实、误报、已修复。
- 作为“能否通过”的阻断来源。

关键约束：

- `BLOCKER` 必须带文件与有效行号或 hunk，否则不能进入聚合。
- 标记误报只改状态，不删除原文。
- 已修复发现必须保留原始证据和处理时间。

### 3.4 ReviewEvidence

定位：`ReviewSnapshot` 内实体。

职责：

- 表达测试、构建、日志、截图、接口样例、迁移检查和部署预检结果。
- 关联变更单元，也可作为快照级证据。
- 明确区分通过、失败、未执行、不可验证。

关键约束：

- “没有证据”不得落成“已验证”。
- 证据必须可追溯，至少保存来源类型与来源 ID；运行日志同时保存 `taskRunId`。
- 证据正文只保存已截断摘要，完整内容通过现有运行记录或测试记录入口查看。

### 3.5 ReviewDecision

定位：独立聚合根，只追加不修改。

字段：

- `ReviewDecisionId`
- `ReviewSnapshotId`
- 结论：`APPROVED / CHANGES_REQUESTED / REJECTED`
- 操作者 ID
- 意见
- 创建时间

关键约束：

- 同一快照可以有多条历史结论，但只有最新一条与快照当前状态一致。
- 结论必须绑定快照 ID，不能只绑定任务 ID。
- 部署审计只引用通过的 `ReviewDecisionId`。

## 四、跨上下文引用

`review` 不直接引用 `Task`、`TaskRun`、`Project` 聚合或其实体。

领域内使用本地强类型 ID：

- `ReviewTaskId`
- `ReviewTaskRunId`
- `ReviewProjectId`

应用服务负责把执行上下文与项目上下文的 ID 映射进来。这样 `review.domain` 只依赖自身领域和
`shared`，不会出现跨上下文领域对象引用。

```java
public interface ReviewSnapshotRepository {
```

## 六、端口与适配器

### 6.1 ReviewDiffReader

```java
public interface ReviewDiffReader {
    ReviewDiff read(ReviewDiffRequest request);
}
```

输入只包含项目目录、任务开始 base ref 与执行器上报文件；输出是领域值对象 `ReviewDiff`，
包含：

- `baseRef`
- `headRef`
- `diffHash`
- 文件清单与每个文件的增删行数
- 完整 unified diff
- 是否 Git 仓库

实现要求：

- 使用 `git diff --no-ext-diff --binary=false <baseRef> --` 读取已跟踪文件变更。
- 未跟踪文件逐个读取元信息与文本内容，二进制只保留路径、类型和大小。
- diff 哈希使用 SHA-256，输入为稳定排序后的文件元信息与原始 diff 字节。
- 非 Git 目录降级为文件清单；不伪造 commit。
- 输出大小超过上限时截断正文并设置 `truncated=true`，哈希仍基于完整字节流计算。

### 6.2 ReviewAnalyzer

```java
public interface ReviewAnalyzer {
    ReviewAnalysis analyze(ReviewAnalysisRequest request);
}
```

默认实现先使用保守规则完成分组与风险识别，再由只读 Codex 预审增强标题、原因与发现。
Codex 不可用、超时或输出不合法时退回规则结果：

- 迁移、认证权限、密钥证书、部署脚本、公共契约、删除操作一律至少高风险。
- 生成文件、锁文件、纯格式化和测试补充单独分组。
- 规则无法确认意图时明确输出“尚未确认意图”，不生成无代码位置的阻断问题。
- AI 输出解析失败保留规则结果，不阻塞快照生成；只有规则预审本身失败时才把
  `analysis_status` 标为失败。

后续 Codex 预审适配器只能实现该端口，不能把 JSONL 或执行器 DTO 泄漏进 `regent-core`。

## 八、应用服务契约

### 8.1 ReviewSnapshotService

```java
ReviewSnapshot generate(ReviewTaskId taskId, ReviewTaskRunId runId);
Optional<ReviewSnapshot> current(ReviewTaskId taskId);
ReviewSnapshot markViewed(ReviewTaskId taskId, ReviewChangeUnitId unitId, UserId operator);
```

执行规则：

- 只对成功运行生成快照。
- 先计算 diff，再在同一事务内把同任务旧的有效快照置为 `EXPIRED`，最后保存新快照。
- 同一 `task_run_id` 重复生成必须幂等返回已存在快照。
- 分析失败保留快照和 diff 事实，`analysis_status=FAILED`，用户仍可查看原始 diff。
- 生成失败记录运行事件 `platform.review.failed`，不影响任务和运行记录。

### 8.2 ReviewDecisionService

```java
ReviewDecision decide(ReviewDecisionCommand command);
void markFinding(ReviewFindingCommand command);
```

执行规则：

- 加载任务归属并校验项目属于当前用户。
- 通过、要求修改、驳回分别调用快照领域方法，再追加 `ReviewDecision`。
- 通过前由聚合校验阻断问题和高风险必看单元。
- 要求修改生成一条待下发的任务调整方向，复用原任务会话，不新建无上下文任务。
- 部署门禁只认最新的人工通过结论。

## 九、DTO 契约

只放在 `regent-interfaces/review/interfaces/dto`，不序列化领域对象。

### 9.1 读模型

`ReviewSnapshotResponse`：

- 快照 ID、任务 ID、运行 ID、项目 ID
- base/head、diff 哈希、Git 降级标记
- 文件数、增删行数、审阅状态、分析状态
- 必要查看数、已查看数、未处理发现数、是否可满足通过与部署条件
- 变更单元、发现、证据、历史结论

`ReviewChangeUnitResponse`：

- ID、类别、风险、标题、原因、模块、文件列表、关键 hunk
- 是否必看、查看时间

`ReviewFindingResponse`：

- ID、级别、状态、标题、描述、影响、文件、行号、建议动作

`ReviewEvidenceResponse`：

- ID、类型、状态、标题、命令、摘要、来源类型与 ID、时间

### 9.2 写模型

- `ReviewDecisionRequest { decision, comment }`
- `ReviewFindingStatusRequest { status }`
- `DeploymentRunRequest { projectId, taskId }`

`comment` 对“要求修改”和“驳回”必填，长度上限 4000 字符。

## 十、接口设计

嵌入现有任务详情和交付流程，不新增顶级菜单：

- `GET /api/tasks/{taskId}/review`：当前快照摘要与全部审阅事实。
- `POST /api/tasks/{taskId}/review/generate`：手工补生成或重试生成。
- `POST /api/tasks/{taskId}/review/units/{unitId}/viewed`：记录已查看。
- `PATCH /api/tasks/{taskId}/review/findings/{findingId}`：标记属实、误报或已修复。
- `POST /api/tasks/{taskId}/review/decisions`：通过、要求修改或驳回。
- `GET /api/tasks/{taskId}/review/diff`：按需读取完整 diff。
- `POST /api/deployments/{id}/run`：请求体新增 `taskId`；服务端强制门禁。

## 十一、错误与失败关闭

- 无有效快照：部署失败 `REVIEW_REQUIRED`。
- 快照已过期：部署失败 `REVIEW_EXPIRED`。
- 最新结论不是通过：部署失败 `REVIEW_NOT_APPROVED`。
- 当前 diff 哈希与通过快照不一致：先把快照置为过期，再返回 `REVIEW_EXPIRED`。
- 存在未处理阻断问题：审阅通过失败 `BLOCKING_FINDINGS_OPEN`。
- 高风险必看单元未查看：审阅通过失败 `REQUIRED_UNITS_UNVIEWED`。
- Git diff 读取失败：快照生成失败并记录诊断，不影响任务完成。

## 十二、最小纵向切片

| 切片 | 范围 | 验收 |
|---|---|---|
| S1 审阅事实 | base ref 捕获、V42、ReviewSnapshot 聚合、Git diff 端口、成功收场触发、查询 API、任务详情入口 | 任务完成后能打开快照，重复读取一致，非 Git 项目可降级 |
| S2 分组与证据 | ChangeUnit、风险规则、测试/运行证据、关键 hunk、风险排序与折叠策略 | 首屏 3–8 个主单元，高风险默认展开，生成/锁文件折叠，证据状态可区分 |
| S3 发现与结论 | ReviewFinding、人工查看、误报/修复状态、通过/修改/驳回、ReviewDecision 审计 | 阻断问题阻止通过，结论有操作者和时间，要求修改进入原任务 |
| S4 失效与门禁 | 新 diff 哈希使旧结论过期、部署请求任务上下文、部署记录关联快照 | 代码变化后再次部署被阻断，已通过快照可作为部署依据 |
| S5 体验与审计 | 任务详情审阅区、执行控制塔入口、交付页阻断原因、关键操作审计 | 不新增顶级菜单，审阅到部署路径连续可操作 |

## 十三、实施顺序与验证

1. 先写 `review` 领域模型单测，覆盖状态迁移、通过守卫、发现状态与哈希绑定。
2. 实现 diff 端口与 Git 适配器单测，覆盖 Git、非 Git、二进制、未跟踪文件、哈希稳定性。
3. 增加 V42 和 MyBatis 仓储，跑仓储与 Spring 装配测试。
4. 接入任务成功收场，跑 `regent-core` 与执行链路测试。
5. 实现审阅应用服务和 REST，覆盖账户隔离、幂等、过期与门禁。
6. 最后接入任务详情和执行控制塔 UI，做前端类型检查与关键交互验证。
7. 提交前跑 `mvn -q clean verify`；若本机 MySQL 不可用，集成测试结果如实记录。

## 十四、风险与取舍

| 风险 | 取舍 |
|---|---|
| diff 内包含密钥或 Token | 落库前统一脱敏，敏感文件正文不进入摘要；原始 diff 仍只对项目所有者开放 |
| 超大 diff 撑大数据库 | 设置单快照正文上限与截断标记，哈希始终基于完整字节流计算，完整内容超限时明确不可审阅 |
| AI 分析不可用 | 快照和规则分组先落事实，AI 失败只降低解释质量，不阻塞任务完成 |
| 工作区在执行结束后继续变化 | 部署前重新算哈希，不只信快照生成时的状态 |
| 无 Git 项目的审阅可信度较低 | 明确标记 `gitRepository=false`，部署默认要求人工通过 |
| 审阅成为发布瓶颈 | MVP 只拦正式部署；运行记录、任务详情和代码事实仍可正常查看 |
