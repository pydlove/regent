## 一、背景

当前审阅通过后已经支持在平台内生成提交说明、填写 6 位 Bug 编号并创建本地 Git 提交。
成功提交后，审阅快照会保存：

- `commit_sha`
- `commit_message`
- `committed_by`
- `committed_at`

这解决了“哪次审阅对应哪个提交”的基本追溯问题，但仍存在四个缺口：

1. 只能看到成功结果，提交失败没有记录。
2. 一个任务后续产生新的审阅快照和提交时，没有独立历史。
3. 没有按项目、任务、提交人、时间或状态检索的入口。
4. 审阅快照承担了代码事实和提交历史两种职责，后续扩展 Push、远端校验时会继续膨胀。

因此需要把 Git 提交从“审阅快照上的一个结果字段”升级为独立的只追加审计记录。

## 二、目标

### 1. 业务目标

- 建立任务、运行记录、审阅结论、提交动作和 Commit SHA 之间的完整审计链路。
- 让用户能确认某次 AI 执行的代码是否真正形成了提交。
- 让企业可以查询和复盘平台发起的 Git 提交。
- 为后续 Push、远端校验和发布门禁提供稳定的数据基础。

### 2. 用户目标

- 在任务详情中直接看到本次任务提交了什么。
- 在交付页查询项目下的提交记录。
- 能区分成功和失败，并能看到失败原因。
- 能复制提交说明、Bug 编号和 Commit SHA。
- 能从提交记录跳回对应任务和审阅快照。

### 3. 非目标

- 不复制完整 Git 仓库历史。
- 不替代 GitHub、GitLab、Gitee 的提交页面和代码托管能力。
- 不实现分支合并、Pull Request、Code Review 评论和冲突解决。
- 不允许编辑或删除历史提交记录。
- MVP 不自动 Push 到远端；Push 作为后续独立需求。

## 三、核心产品模型

### 1. GitCommitRecord

平台发起的一次 Git 提交尝试。

它是独立记录，不是 Git commit 对象的副本：

- 一个审阅快照可以有多次失败尝试，但最多只能有一次成功提交。
- 失败尝试与成功提交都保留。
- 记录成功后再出现新的审阅快照，可产生新的提交记录。

### 2. 记录与审阅快照的关系

```text
Task
  └─ TaskRun
       └─ ReviewSnapshot
            ├─ ReviewDecision（整单人工结论）
            ├─ ReviewChangeUnit[]（逐 diff 结论）
            └─ GitCommitRecord[]（提交尝试）
```

GitCommitRecord 必须关联：

- 任务 ID
- 运行记录 ID
- 项目 ID
- 审阅快照 ID
- 整单审阅结论 ID

### 3. 提交状态

| 状态 | 含义 |
|---|---|
| `RUNNING` | 已创建记录，正在执行 Git 提交 |
| `SUCCEEDED` | Git 提交创建成功，已有 Commit SHA |
| `FAILED` | Git 提交失败，保留失败原因 |

不允许通过页面直接把失败记录改成成功。

## 四、功能需求

### GIT-01 记录每一次提交尝试

优先级：P0

要求：

- 点击“提交 Git”后，先创建 `RUNNING` 记录，再执行 Git。
- 成功创建提交后写入 Commit SHA、分支和时间。
- 失败时写入失败状态、失败原因和可读输出。
- 记录创建后不允许物理删除。

验收：

- 失败提交也会出现在任务详情和提交列表中。
- 成功记录能从任务追溯到审阅快照和人工结论。

### GIT-02 绑定审阅事实

优先级：P0

要求：

- 提交前必须存在当前有效审阅快照。
- 最新整单审阅结论必须为 `APPROVED`。
- 当前 diff 哈希必须与审阅快照一致。
- 必看 diff 项都必须已逐项通过。
- 记录保存审阅快照 ID 和整单结论 ID。

验收：

- 未审阅、审阅过期或仍有 diff 被驳回时，不能创建提交记录。
- 任意提交记录都能回溯到对应审阅结论。

### GIT-03 限定提交文件

优先级：P0

要求：

- 只提交当前审阅快照包含的文件。
- 暂存区已有其他改动时失败关闭。
- 不把未审阅文件、未跟踪文件或其他任务改动混入提交。
- 记录保存实际提交文件清单。

验收：

- 未审阅改动仍保留在工作区，且不进入该 Commit。
- 文件清单与 Git 实际提交内容一致。

### GIT-04 生成并校验提交说明

优先级：P0

要求：

- 使用企业 Git 提交规范生成建议说明。
- 默认格式为 `type(6位Bug编号): 中文说明`。
- 用户可以编辑最终说明。
- 后端再次校验提交规范。
- 记录保存 Bug 编号和最终提交说明。

验收：

- Bug 编号不足 6 位或非数字时不能提交。
- 修改后的说明不符合企业规范时不能提交。

### GIT-05 任务详情中的提交摘要

优先级：P0

要求：

- 审阅通过区域展示提交入口。
- 提交成功后展示最新成功提交：
  - 提交说明
  - Bug 编号
  - 短 SHA
  - 分支
  - 提交时间
- 存在失败记录时展示最近一次失败原因。
- 支持“查看全部提交记录”。

验收：

- 用户不进入交付页也能知道任务是否已经提交。
- 成功记录优先于失败记录展示。

### GIT-06 提交记录列表

优先级：P0

要求：

- 在“交付”页增加“Git 提交”标签页。
- 默认按提交时间倒序排列。
- 列表字段：
  - 任务标题
  - 项目
  - Bug 编号
  - 提交说明
  - 分支
  - 短 SHA
  - 状态
  - 操作人
  - 提交时间
- 支持按项目、状态、关键字和时间筛选。
- 关键字可匹配任务标题、提交说明、Bug 编号和 Commit SHA。

验收：

- 用户能在交付页快速定位某次 AI 任务的提交。
- 仅能看到当前账号所属项目的记录。

### GIT-07 提交详情

优先级：P0

要求：

详情展示：

- 关联任务、运行记录和审阅快照
- 完整提交说明
- Bug 编号
- 完整 Commit SHA
- 项目、分支、仓库路径
- 提交文件清单
- 操作人和时间
- 成功或失败结果
- 失败原因和脱敏后的输出摘要

验收：

- 可从详情跳回任务和审阅工作区。
- Commit SHA 和提交说明可一键复制。

### GIT-08 失败重试

优先级：P1

要求：

- 失败记录本身不可修改。
- 在审阅快照仍有效时允许重新发起一次新尝试。
- 重试会创建新的 GitCommitRecord，不覆盖旧记录。

验收：

- 失败原因修正后可成功提交。
- 提交历史同时保留失败和成功尝试。

### GIT-09 幂等与并发保护

优先级：P0

要求：

- 同一审阅快照最多一个成功提交。
- 重复点击或并发请求不能创建两个成功提交。
- Git 操作前再次检查当前分支、HEAD 和暂存区。

验收：

- 双击“提交 Git”不会产生重复 Commit。
- 并发请求只有一个成功，另一个明确返回已提交。

### GIT-10 敏感信息保护

优先级：P0

要求：

- 失败输出、命令输出和日志摘要必须脱敏。
- 不记录密码、Token、私钥和环境变量值。
- 仓库路径只保存项目路径，不保存 SSH 凭据。

验收：

- 提交失败日志中不出现明文凭据。
- API 和页面均不回传敏感值。

## 五、页面信息架构

### 1. 任务详情

```text
变更审阅
  ├─ 审阅状态
  ├─ 逐 diff 决策
  ├─ 提交 Git
  └─ 最新提交摘要
       ├─ 提交说明
       ├─ Bug 编号
       ├─ 分支 + 短 SHA
       └─ 查看全部提交
```

### 2. 交付页

交付页现有标签：

- 部署
- 测试

新增：

- Git 提交

不新增一级菜单。

### 3. 提交详情

使用右侧抽屉或弹窗，不新开一级页面。

## 六、权限与数据隔离

- 提交记录继承项目租户归属。
- 用户只能查看自己项目下的提交。
- 提交动作只允许当前项目归属账号发起。
- 历史记录对所有当前账号可见，但不可编辑或删除。
- 后续如加入管理员角色，管理员查询权限另行设计。

## 七、数据保留

- 提交记录长期保留。
- Commit 被远端删除或分支被删除，不影响平台审计记录。
- 任务逻辑删除后，提交记录仍保留任务 ID 和任务标题快照。
- 项目逻辑删除后，保留历史记录用于审计，默认列表不再展示。

## 八、成功指标

| 指标 | 目标 |
|---|---|
| 已审阅任务中成功提交比例 | 可观测并持续提升 |
| 提交失败可定位比例 | 100% 有可读失败原因 |
| 提交记录到任务追溯成功率 | 100% |
| 重复提交事故 | 0 |
| 未审阅代码进入平台提交 | 0 |

## 九、分期范围

### MVP

- GitCommitRecord 数据模型与迁移
- 成功/失败提交记录
- 任务详情摘要
- 交付页 Git 提交列表
- 提交详情
- 权限隔离和幂等保护

### 后续

- Push 到远端
- 远端分支和远端 SHA 校验
- PR/MR 链接
- CI 状态关联
- 人工补录外部提交
- 导出审计报表

## 十、明确不做

- 不做完整 Git 客户端。
- 不做平台内代码编辑器。
- 不维护一份与 Git 重复的提交树。
- 不允许页面绕过审阅直接提交。
- 不允许用户在历史记录中修改提交 SHA 或提交说明。
