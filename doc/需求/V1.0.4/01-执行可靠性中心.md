## 一、背景与问题

Regent 已经支持本机 Codex、外部设备代理、任务队列、执行租约、决策阻塞和部署执行，但执行链路仍存在以下问题：

1. 后端重启后，排队任务可能没有设备接手，用户只看到“排队中”。
2. 设备已经离线、Codex 不可用或项目目录不存在时，任务仍可能进入执行状态。
3. 同一任务可能被重复投递或重复认领，缺少统一的幂等边界。
4. 设备心跳、执行租约和任务状态之间没有一套用户能理解的健康判断。
5. Runtime 升级包缺少依赖时，客户端可能安装失败、回滚、再次提示同一版本。
6. 任务失败后没有统一的“最后成功阶段、失败阶段、建议操作”。
7. 用户无法区分等待并发位、等待设备、等待决策和异常卡住。

V1.0.4 必须把这些问题收敛为一个统一的执行可靠性底座，而不是继续在页面层增加临时判断。

## 二、目标

### 1. 业务目标

- 保证任务从创建到收场只有一个有效执行主体。
- 保证平台重启、设备重启和网络短时中断后，任务可以恢复。
- 保证升级失败不会形成重复更新死循环。
- 让所有执行失败都有可操作的恢复路径。
- 为工作台提供稳定的执行事件和健康状态来源。

### 2. 用户体验目标

- 用户能看懂任务是在正常排队、等待设备、等待决策，还是已经异常。
- 任务超过合理时间没有推进时，系统主动提示原因。
- 失败后的第一步操作明确，不需要用户先收集日志。
- 设备接入和客户端升级不再要求用户理解内部 Runtime、租约或端口机制。
- 同一任务不会因为重复心跳被重复执行。

### 3. 非目标

- 不实现跨地域调度。
- 不实现复杂资源配额和成本中心。
- 不重写现有任务状态机。
- 不在本版本实现任意阶段回滚。
- 不允许 AI 自动改动生产服务器。

## 三、核心模型

### 1. 业务状态与健康状态分离

业务状态继续使用现有任务运行状态，例如：

- 待执行。
- 排队中。
- 执行中。
- 等待决策。
- 已完成。
- 失败。
- 已终止。

健康状态由执行事件、心跳和租约推导，至少包括：

| 健康状态 | 含义 |
|---|---|
| 正常 | 有心跳或近期事件，状态推进符合预期 |
| 缓慢 | 超过阈值没有新事件，但仍有执行主体在线 |
| 疑似卡住 | 超过更长时间没有推进，需要用户关注 |
| 设备失联 | 设备心跳和设备租约均已失效 |
| 状态未知 | 信息不足，不能判断 |

健康状态不得直接修改任务业务状态，不得由前端直接写入。

### 2. 执行上下文

每次执行至少记录：

- 任务 ID。
- 执行记录 ID。
- 项目 ID。
- 设备 ID。
- 执行者。
- Codex 会话 ID。
- 工作区路径。
- 当前阶段。
- 最后事件时间。
- 最后心跳时间。
- 租约到期时间。
- 失败分类。

### 3. 状态与操作关系

| 当前情况 | 用户可见操作 |
|---|---|
| 等待执行位 | 保持排队、取消 |
| 等待设备 | 更换设备、取消 |
| 设备失联 | 重新连接、重新派发、取消 |
| 执行缓慢 | 查看详情、继续等待、取消 |
| 疑似卡住 | 查看诊断、重试、终止 |
| 等待决策 | 批准、驳回、查看会话 |
| 失败 | 查看原因、重试、继续执行 |

所有操作必须经过领域状态守卫，并在执行记录中留下操作者、时间和结果。

## 四、功能需求

### EXE-01 持久化排队与幂等派发

任务一旦进入排队状态，必须能够被持久化设备心跳重新发现。

规则：

- 排队任务必须按账号、项目和依赖关系过滤。
- 任务依赖未完成时不能投递。
- 已终止、已完成或已删除的任务不能被重新投递。
- 同一任务在同一时刻最多存在一个有效执行租约。
- 重复心跳、重复请求可返回同一状态，但不能创建第二个有效执行记录。
- 设备一次心跳最多领取有限数量的任务，避免瞬间创建大量执行循环。

验收：

- 后端重启后，数据库中的排队任务能在设备下一次心跳时被重新发现。
- 其他账号的任务不会投递给当前设备。
- 有未完成依赖的任务保持不可领取。
- 同一任务连续收到多次心跳，不产生多个有效执行记录。

### EXE-02 设备心跳与执行租约

设备必须通过心跳证明在线，执行必须通过租约证明仍在运行。

规则：

- 设备心跳包含设备 ID、主机名、平台、Codex 状态和最后在线时间。
- 执行租约包含执行记录 ID、执行者、租约到期时间和最后活动时间。
- 心跳只续租当前执行者持有的执行记录。
- 租约过期后平台释放执行位，并将任务标记为可恢复状态。
- 设备代理应限制单个设备同时创建的执行数量。
- 设备离线时不能只依赖设备端自行判断，平台必须能独立发现。

验收：

- 设备停止心跳后，平台在租约阈值内将执行标记为失联或可恢复。
- 任务执行结束后租约立即释放。
- 过期执行记录不能继续上报成功结果。
- 非当前执行者不能续租或上报。

### EXE-03 重启恢复与卡住检测

平台启动、客户端重启或设备代理重启后，必须恢复可恢复的执行。

规则：

- 启动时扫描未收场执行记录，区分可续跑、需等待决策、需人工处理和已失联。
- 有 Codex 会话且执行上下文有效的任务，优先续跑。
- 没有有效会话的任务回到排队或待执行，不得凭空标记成功。
- 长时间没有事件的任务进入“缓慢”或“疑似卡住”。
- 卡住检测不能仅根据任务总耗时，必须结合最后活动时间和心跳。
- 用户终止的任务不得被恢复器重新拉起。

验收：

- 后端重启后，正常排队任务不会消失。
- 执行中断的任务在界面显示恢复结果，而不是一直显示执行中。
- 终止后重启不会重新执行。
- 设备代理重启后不会无限重试已经终止的任务。

### EXE-04 设备与 Codex 自检

任务派发前必须完成最小执行环境检查。

检查项：

- 设备代理是否在线。
- Codex 是否可执行。
- Codex 版本和路径是否可读取。
- 项目目录是否存在。
- 当前账号是否有项目访问权。
- 设备是否支持当前任务所需的运行平台。
- Runtime 与客户端壳是否兼容。

检查失败时：

- 不创建有效执行记录。
- 不消耗执行位。
- 给出用户能执行的处理动作。
- 记录结构化失败原因。

验收：

- 设备未在线时，任务不会进入执行中。
- Codex 不存在时，用户看到安装或路径修复提示。
- 项目目录不存在时，用户看到选择项目目录的入口。
- 用户更换设备后可以重新派发。

### EXE-05 客户端升级安全

客户端 Runtime 更新必须满足：

- 发布包包含 Runtime 启动所需的全部本地依赖。
- 下载后校验文件大小、SHA-256 和签名。
- 安装时校验包内版本与发布清单一致。
- 首次启动失败自动回滚到上一个有效 Runtime。
- 记录失败版本，同一失败版本不得反复弹窗。
- 新版本健康确认前，不把更新标记为完成。
- 新发布包必须打包启动入口、更新策略、设备代理和更新窗口资源。

验收：

- 缺少依赖的 Runtime 不会进入候选版本。
- 安装失败后回到旧版本，且不重复提示同一失败版本。
- 更新提示只对新的发布码再次出现。
- 更新窗口固定尺寸、正文左对齐、无滚动条。

### EXE-06 执行诊断

为用户和后续工作台提供统一诊断数据：

- 失败分类。
- 最后成功阶段。
- 失败阶段。
- 是否可重试。
- 是否需要更换设备。
- 是否需要人工决策。
- 脱敏后的诊断摘要。

诊断摘要不得包含密码、Token、完整环境变量值和完整附件正文。

## 五、用户故事

### 故事 1：服务重启后继续执行

作为项目负责人，我希望服务重启后排队任务仍然能被设备领取，这样我不需要手动重新派发。

### 故事 2：设备离线时知道怎么办

作为操作者，我希望任务等待设备时能看到设备名称和离线原因，这样我可以启动代理或切换设备。

### 故事 3：升级失败不会反复弹窗

作为客户端用户，我希望一次失败的更新自动回滚，并且同一版本不再无限提示，这样我可以继续工作。

### 故事 4：终止后不会被重新拉起

作为用户，我终止任务后不希望在服务或设备重启时再次执行它。

## 六、技术边界

### 1. 领域层

- 状态迁移继续在任务、执行记录等聚合根方法内完成。
- 不允许在控制器或 Mapper 中直接修改状态。
- 设备、执行事件和升级状态通过端口抽象，不把具体框架类型带进核心域。

### 2. 应用层

- 应用服务负责编排任务、设备、租约和恢复流程。
- 幂等键、执行占用和恢复规则必须有明确的事务边界。
- 不让工作台或前端自行拼接业务状态。

### 3. 基础设施层

- 设备心跳和租约的持久化实现放在 infrastructure。
- 任务、执行记录、事件查询应提供可复用的读模型。
- Runtime 包完整性检查属于发布和启动链路，不得绕过签名校验。

### 4. 数据库

新增字段必须通过新的 Flyway 迁移完成，至少考虑：

- 执行记录最后心跳时间。
- 执行记录最后事件时间。
- 设备标识或设备会话标识。
- 失败分类和诊断摘要。
- Runtime 失败版本或等价状态。

## 七、验收场景

### 场景 1：排队任务恢复

**Given** 任务已进入排队，后端随后重启  
**When** 已配对设备下一次发送心跳  
**Then** 当前账号对应的可执行排队任务被重新发现  
**And** 设备开始领取后，任务进入执行中

### 场景 2：任务已终止

**Given** 设备正在等待执行位，任务随后被用户终止  
**When** 设备再次请求排队或认领  
**Then** 返回明确的不可执行原因  
**And** 设备停止重试，不再持续打印 HTTP 错误

### 场景 3：客户端更新失败

**Given** 新 Runtime 缺少启动依赖  
**When** 客户端安装并重启  
**Then** 启动失败，自动回滚到上一个 Runtime  
**And** 界面不再重复提示同一个失败版本  
**And** 只有新的发布码才会重新提示更新

### 场景 4：设备离线

**Given** 任务已经分配给设备  
**When** 设备超过心跳阈值没有响应  
**Then** 任务健康状态显示设备失联  
**And** 用户能看到重新连接、换设备或取消

## 八、成功指标

| 指标 | 衡量方式 |
|---|---|
| 任务恢复率 | 重启后重新进入可执行或已收场状态的任务比例 |
| 重复执行率 | 同一任务产生多个有效执行租约的比例 |
| 无解释停留时长 | 任务停留超过阈值但无原因记录的时间 |
| 设备接入成功率 | 首次启动设备代理后成功检测 Codex 的比例 |
| 升级成功率 | Runtime 安装后第一次启动成功的比例 |
| 更新重复提示次数 | 同一失败发布码在客户端弹窗的次数 |

## 九、风险与待确认项

| 风险 | 影响 | 建议 |
|---|---|---|
| 任务健康状态与现有状态混用 | 页面和状态机出现双重真相 | 健康状态作为读模型或独立字段，不替代业务状态 |
| 设备绑定到账号而非项目 | 多项目环境下任务投递不精准 | 评审确认绑定层级 |
| 恢复规则过于激进 | 已终止任务被重新拉起 | 恢复器必须读取终止和删除事实 |
| Runtime 兼容多客户端壳 | 旧客户端出现启动失败 | 明确最低 shell 版本和降级提示 |
