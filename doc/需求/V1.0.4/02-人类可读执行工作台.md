## 一、背景与问题

Regent 已经记录 Codex 的 JSONL、部署日志、测试结果和执行事件，但用户看到的仍然是大量技术信息：

1. 用户不知道任务当前处于准备、分析、修改、验证还是部署阶段。
2. Codex 的事件、命令输出和错误堆栈混在一起，默认信息密度过高。
3. 失败时只显示退出码或一段原始错误，没有说明影响和下一步。
4. 等待决策、设备离线、执行位不足等不同原因被统一显示成“运行中”或“排队中”。
5. 用户必须打开多个地方才能理解一次执行的全貌。
6. 失败后无法快速复制一份脱敏诊断信息给其他人。

V1.0.4 需要把执行事件翻译成用户可以理解和操作的产品语言。

## 二、目标

### 1. 业务目标

- 降低任务执行异常的人工解释成本。
- 提高用户对自动执行的信任。
- 减少用户查看原始日志和手工排查的次数。
- 为项目级交付提供统一的执行展示组件。

### 2. 用户体验目标

- 打开任务详情后，用户能在首屏回答“现在怎样了、为什么、我该做什么”。
- 技术详情仍然可追溯，但不抢占主要注意力。
- 大多数失败不打开原始 JSONL 也能定位原因。
- 用户可以在时间线中看到一次执行的阶段变化和关键结果。
- 执行卡住时页面主动显示，而不是要求用户猜。

### 3. 非目标

- 不在本版本实现 AI 自动修复所有失败。
- 不保证对每一行 Codex 输出做产品化翻译。
- 不隐藏原始执行记录。
- 不把执行工作台做成独立于任务和交付的新菜单。

## 三、核心展示模型

### 1. 执行摘要

顶部摘要必须包含：

- 任务或交付名称。
- 项目。
- 执行类型。
- 业务状态。
- 健康状态。
- 当前阶段。
- 已运行时间。
- 最后活动时间。
- 当前设备或执行环境。

### 2. 用户时间线

时间线只展示对用户有意义的节点：

1. 已创建。
2. 已进入队列。
3. 已分配设备。
4. 已验证执行环境。
5. 已开始分析。
6. 已修改文件。
7. 正在运行验证。
8. 等待人工决策。
9. 正在部署。
10. 已完成、失败或终止。

每个节点包含：

- 用户可读标题。
- 一到两句话的摘要。
- 发生时间。
- 当前是否进行中。
- 可展开的技术详情。

### 3. 失败摘要卡

失败或疑似卡住时，在详情顶部显示：

- 失败分类。
- 发生了什么。
- 影响是什么。
- 建议用户执行什么操作。
- 是否可以重试。
- 是否需要换设备或人工批准。

### 4. 技术详情

技术详情默认折叠，至少包含：

- 原始 JSONL 事件。
- 命令和退出码。
- 文件改动。
- 请求和响应摘要。
- 完整错误堆栈。
- 脱敏后的环境变量键名。

技术详情不得包含密码、Token、完整密钥和完整附件正文。

## 四、功能需求

### OBS-01 统一执行时间线

任务执行、部署执行和测试执行使用同一套时间线组件。

要求：

- 事件顺序稳定。
- 重连后能补齐缺失事件。
- 重要阶段不能被大量低价值事件淹没。
- 用户可展开查看原始事件。
- 执行完成后摘要保留。

验收：

- 同一执行在新窗口和刷新后展示一致。
- 事件乱序到达时按事件序号或时间重建。
- 没有关键阶段时不能伪造阶段。

### OBS-02 用户可读状态文案

状态文案必须说明原因，不使用单独的技术状态码。

示例：

| 技术情况 | 用户文案 |
|---|---|
| QUEUED 且等待执行位 | 正在等待执行位，已有任务占满当前并发上限 |
| QUEUED 且无在线设备 | 正在等待设备，请启动设备代理或切换设备 |
| BLOCKED 且待决策 | 等待你的批准，执行已暂停 |
| 运行中且心跳正常 | 正在分析项目并执行修改 |
| 运行中且最后活动超时 | 执行暂时没有新进展，系统正在确认是否卡住 |
| 设备失联 | 执行设备已离线，可以重新连接或换设备 |

验收：

- 用户不阅读原始日志也能理解文案。
- 文案中不能出现未脱敏的敏感信息。
- 同一业务状态在不同页面使用同一套文案。

### OBS-03 失败诊断与下一步

每次失败至少展示：

- 用户可读失败原因。
- 最后成功阶段。
- 失败阶段。
- 影响范围。
- 可执行动作。

动作按情况提供：

- 重试。
- 继续会话。
- 更换设备。
- 打开项目目录设置。
- 打开 Codex 安装或环境设置。
- 查看技术详情。
- 复制诊断信息。

验收：

- 失败任务详情首屏有明确的下一步按钮。
- 不是所有失败都提供“重试”，不可恢复的失败必须说明原因。
- 操作后状态及时刷新。

### OBS-04 等待决策

等待决策是用户最需要接管的状态之一。

要求：

- 在时间线中标记为等待人工。
- 在任务详情和全局待办中都可见。
- 展示问题摘要和决策等级。
- 提供批准、驳回、查看完整上下文。
- 处理完成后显示续跑结果。

验收：

- 用户从工作台、任务详情和待办入口进入时看到同一决策。
- 决策处理完成后不会重复显示为待处理。
- 终止任务后关联待决策事项关闭。

### OBS-05 实时刷新与断线恢复

执行详情支持实时刷新，但在断线时不能让页面误以为任务仍在正常推进。

要求：

- 网络断线后显示连接状态。
- 重新连接后补齐执行快照。
- 长时间没有事件时显示“最后活动时间”。
- 不要求用户刷新整页才能看到任务收场。

### OBS-06 执行操作区

操作区固定在详情底部或顶部，至少包括：

- 终止。
- 重试。
- 继续会话。
- 调整方向。
- 更换设备。
- 查看关联部署。

操作必须根据当前状态显示，不可用操作给出原因。

### OBS-07 诊断复制

提供“复制诊断信息”按钮，复制内容至少包含：

- 任务和执行记录 ID。
- 项目名称。
- 当前业务状态和健康状态。
- 当前阶段。
- 设备和执行器。
- 最后成功阶段。
- 失败摘要。
- 脱敏后的事件尾部。

复制内容不得包含密码、Token 或完整环境变量值。

## 五、页面与交互要求

### 1. 任务详情

建议结构：

1. 状态摘要。
2. 失败或决策提示卡。
3. 用户时间线。
4. 关键产物和改动。
5. 技术详情折叠区。
6. 操作区。

### 2. 工作台控制塔

控制塔只展示高层状态：

- 正在执行。
- 等待决策。
- 等待设备。
- 异常卡住。
- 已完成。

点击记录进入完整执行详情，不在首屏堆叠全部技术日志。

### 3. 交付页

部署和发布记录复用同一执行详情组件。

交付详情额外展示：

- 目标环境。
- 服务器。
- 发布版本。
- 部署阶段。
- 回滚状态。

## 六、技术边界

- 原始事件解析留在 Codex 和部署适配器中。
- 应用层把原始事件转换为稳定的执行事件读模型。
- 用户文案映射不应散落在多个 Vue 组件中，建议集中到共享映射或无框架领域语言层。
- 技术详情和用户摘要必须来自同一事件事实，不允许前端根据关键词猜状态。
- 事件上报应支持批量和失败重试，但不能因为单个事件过大阻断整次执行。
- 事件内容超过限制时必须截断并标记，不得丢弃整个摘要。

## 七、验收场景

### 场景 1：任务正常完成

**Given** 用户打开一个正在执行的任务  
**When** 任务完成  
**Then** 时间线依次显示准备、分析、修改、验证和完成  
**And** 技术详情默认收起  
**And** 用户可以查看最终摘要

### 场景 2：任务卡住

**Given** 任务执行中超过阈值没有新事件  
**When** 用户打开任务详情  
**Then** 页面显示疑似卡住和最后活动时间  
**And** 提供诊断、重试或终止  
**And** 不把任务误显示为已完成

### 场景 3：设备离线

**Given** 任务分配到离线设备  
**When** 用户刷新详情  
**Then** 页面显示设备失联  
**And** 提供重新连接或更换设备  
**And** 技术日志仍可展开

### 场景 4：决策等待

**Given** AI 提出 L2 决策  
**When** 用户打开工作台和任务页  
**Then** 两处都显示同一条待处理事项  
**And** 用户批准后执行继续  
**And** 待办数量立即更新

## 八、成功指标

| 指标 | 衡量方式 |
|---|---|
| 首屏可理解率 | 用户不打开技术详情即可说出执行状态的比例 |
| 原始日志查看率 | 未查看原始日志而完成排障的比例 |
| 失败定位时间 | 从打开失败任务到选择下一步的时间 |
| 决策处理时间 | 从进入待办到批准或驳回的时间 |
| 诊断复制使用率 | 用户使用诊断摘要协作排障的比例 |

## 九、风险与待确认项

| 风险 | 影响 | 建议 |
|---|---|---|
| 事件模型不稳定 | 时间线频繁改动 | 先定义稳定事件 schema，再实现 UI |
| 过度翻译原始日志 | 用户误解模型行为 | 摘要必须保留“技术详情可追溯” |
| 事件量过大 | 首屏加载慢 | 后端聚合摘要，原始事件分页 |
| 多业务状态映射不一致 | 页面互相矛盾 | 共享状态文案映射和统一读模型 |
