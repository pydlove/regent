## 一、版本定位

V1.0.3 完成了工作台、执行控制塔、需求澄清与任务拆解，产品已经具备较完整的功能面。

V1.0.4 不继续增加新菜单和新概念，重点解决用户从“能看到功能”到“敢把真实工作交给平台”的信任问题。

本版本主题：

> **可信执行与交付。**

具体表现为三件事：

1. 任务能够稳定执行、恢复和收场，不出现无解释的长时间排队。
2. 用户能够看懂任务正在做什么、为什么停下以及下一步该做什么。
3. 项目能够从任务执行顺利走到部署和发布，失败时不会把线上环境留在不可控状态。

## 二、本版本范围

V1.0.4 只做以下三个需求，其他能力不得挤占核心范围。

| 优先级 | 需求编号 | 名称 | 主要解决的问题 |
|---|---|---|---|
| P0-1 | REG-V104-EXE | 执行可靠性中心 | 任务排队、设备失联、服务重启、客户端升级失败 |
| P0-2 | REG-V104-OBS | 人类可读执行工作台 | 日志难懂、异常原因不明、用户无法接管 |
| P0-3 | REG-V104-DLV | 项目级一键交付闭环 | 环境、服务器、脚本、部署和发布入口分散 |

## 三、需求依赖与开发顺序

```text
执行可靠性中心
    │
    ├── 提供统一的执行状态、健康和恢复事件
    │
    ▼
人类可读执行工作台
    │
    └── 将执行事件转换为用户能理解的时间线和操作建议
             │
             ▼
      项目级一键交付闭环
             │
             └── 复用执行状态、设备检查、部署记录和诊断信息
```

建议按以下顺序实现：

1. 先完成执行可靠性中心的数据模型、状态守卫、设备租约和故障恢复。
2. 再基于稳定事件流实现执行工作台，不允许工作台自己猜测任务状态。
3. 最后接入项目级交付闭环，让部署和发布复用前两项能力。

如果先做工作台或交付向导，而没有稳定状态源，最终会发生三个模块各自判断状态、互相矛盾的问题。

## 四、共同产品原则

### 1. 不新增一级菜单

三个需求都属于现有主流程的深化能力：

- 执行可靠性属于任务、设备和交付的共同底座。
- 人类可读执行工作台放在现有工作台、任务和交付详情中。
- 项目级交付闭环放在现有“交付”入口。

### 2. 状态必须可解释

每条执行状态必须有：

- 业务状态。
- 健康状态。
- 当前阶段。
- 最后活动时间。
- 阻塞原因。
- 用户下一步操作。

### 3. 失败必须可恢复

失败、超时、设备失联和客户端升级失败都必须有明确的恢复路径。恢复动作必须经过状态守卫和审计，不能通过前端直接改状态。

### 4. 技术信息分层展示

默认展示用户能理解的摘要、结论和建议。

原始 JSONL、命令输出、堆栈、请求日志保留在技术详情中，默认折叠。

### 5. 不破坏现有数据和入口

已有任务、执行记录、部署记录、服务器和环境数据继续可用。路由和 URL 不因本版本改造而失效。

## 五、本版本明确不做

- 不增加新的顶级菜单。
- 不做团队 RBAC、组织架构和项目成员权限。
- 不做跨项目需求协同和复杂依赖编排。
- 不做 Kubernetes、云厂商、CI/CD 平台的通用集成平台。
- 不做报表大屏和复杂容量预测。
- 不允许 AI 自动修改线上生产环境。
- 不在本版本重写任务、部署、环境的全部业务模型。

## 六、成功指标

### 北极星指标

**无需人工介入即可完成执行、验证或交付的任务比例。**

### 配套指标

| 指标 | 目标方向 |
|---|---|
| 任务无解释停留比例 | 显著下降，任何超时都有原因和操作 |
| 服务或客户端重启后的任务恢复率 | 持续提升 |
| 同一任务重复执行次数 | 下降到合理范围 |
| 首次设备接入成功率 | 显著提升 |
| 失败原因定位时间 | 控制在 1 分钟内 |
| 部署一次成功率 | 持续提升 |
| 部署失败后的回滚成功率 | 接近 100% |
| 重复更新提示和更新死循环 | 归零 |

具体目标值由技术评审后结合当前真实运行数据确定。

## 七、技术交接要求

技术经理接手开发时必须先完成以下事项：

1. 阅读 `AGENTS.md`、`ARCHITECTURE.md`、`TECH_STACK.md`。
2. 先做技术方案评审，再拆分任务，不得直接把三个需求都塞进一个巨型服务。
3. 遵守领域层零框架依赖、聚合只持有 ID、状态迁移只走领域方法。
4. 执行器、Git、邮件、推送等外部系统继续走端口和适配器。
5. 数据库结构变更只能新增 Flyway 迁移，禁止修改已执行的 V 脚本。
6. 每项需求必须有单元测试、接口测试和至少一个真实场景验收用例。
7. 先在 V1.0.4 分支完成开发和验证，不覆盖已经发布的 B001/B002。

## 八、评审后需要确认的事项

1. 执行健康状态采用数据库持久化，还是根据执行事件实时推导。
2. 设备与任务的绑定是账号级还是项目级；是否支持同一任务切换设备。
3. 执行时间线的第一阶段是否覆盖部署和测试，还是先覆盖任务执行。
4. 一键交付是否允许直接发布生产环境，还是先要求显式确认。
5. 旧 B001 错误 Runtime 是否需要在下个版本做自动清理和兼容提示。
