# Regent V1.0.5 移动端技术评审

| 项目 | 内容 |
|---|---|
| 需求编号 | REG-V105-MOB |
| 文档版本 | v1.2 |
| 状态 | 技术评审已完成，P0 技术验证进行中 |
| 编写日期 | 2026-10-21 |
| 输入 | 手机 App 需求说明书、产品决策记录 |

## 一、技术结论

需求可以进入技术验证，但不能直接把现有 Web 页面封装成 WebView。

推荐方案：

- 使用 `Capacitor + Vue 3 + TypeScript` 构建 Android/iOS App。
- 复用现有 REST API 契约和状态守卫，单独实现手机布局。
- 公网中继继续承载 API 转发，并增加最小化的主机在线监测与离线推送触发。
- 本地 Regent 继续作为业务权限唯一事实源。
- 外部推送通道使用端口 + 适配器，不让 APNs、FCM 或国内厂商 SDK 进入核心域。

## 二、整体架构

```text
Android / iOS App
  │ HTTPS + Bearer
  ▼
Nginx
  ├── /api/mobile/**  → regent-relay server → connector → local Regent
  └── /api/mobile/presence/** → relay presence service
                                  │
                                  ├── APNs / Android push provider
                                  └── 主机在线/离线状态

local Regent
  ├── 业务 API
  ├── 任务、决策、文件库、设备租约
  └── 业务通知 → push adapter → APNs / Android push provider
```

### 信任边界

- App 不可信，所有归属与状态由本地 Regent 再次校验。
- 公网中继不可信，只允许访问本地 `/api`。
- 公网 presence 只能保存主机在线状态、账号订阅关系和推送令牌，不保存业务数据。
- 本地 Regent 不暴露公网端口。
- Codex、MySQL、项目工作区只在执行电脑。

## 三、认证与会话

### 1. 现有能力

现有 `auth_session` 使用哈希后的浏览器会话令牌，支持普通会话与记住登录。

### 2. 手机会话

新增独立 `mobile_auth_session`，不复用浏览器 Cookie 会话：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `user_id` | 账号 |
| `installation_id` | 手机安装实例 |
| `access_token_hash` | Access Token 的 SHA-256 |
| `refresh_token_hash` | Refresh Token 的 SHA-256 |
| `access_expires_at` | 30 分钟 |
| `refresh_expires_at` | 30 天 |
| `last_used_at` | 最后使用时间 |
| `revoked_at` | 撤销时间 |

### 3. 登录与刷新

```text
账号登录/邮箱验证码登录
  → 校验账号与安装实例
  → 返回 Access Token + Refresh Token
  → App 存 Keychain/Keystore
  → Access 快过期时用 Refresh 轮换
```

Refresh Token 每次使用后轮换。旧 Refresh Token 立即失效，检测到重复使用时撤销整个手机会话。

### 4. 敏感操作

批准、驳回、撤销执行电脑、账号注销要求 Step-up Token：

- 生物识别通过后向本地 Regent 请求 5 分钟操作令牌。
- 操作令牌绑定账号、安装实例和动作类型。
- 只能使用一次。

### 5. Nginx 与中继

- App API 不使用 Nginx Basic Auth。
- Nginx 只负责 HTTPS、请求体限制、限流和反代。
- `Authorization: Bearer <mobile-token>` 只面向 Regent 业务认证。
- 连接器与中继之间继续使用独立共享密钥 `Bearer <relay-secret>`，不转发给手机。
- 写请求继续要求 `X-Regent-Relay-Request: 1`。

## 四、公网主机在线监测

### 1. 原因

本地 Regent 无法在自身离线时发送“主机离线”推送，因此公网侧必须有最小在线监测器。

### 2. 状态字段

presence 只保存：

| 字段 | 说明 |
|---|---|
| `relay_instance_id` | 中继实例 |
| `host_id` | 执行主机 |
| `owner_id` | 主机所属账号 |
| `connector_last_seen_at` | 连接器最后心跳 |
| `online_state` | ONLINE/OFFLINE/RECOVERING |
| `state_changed_at` | 状态变化时间 |
| `last_notification_at` | 上次推送时间 |

不保存任务、项目名、路径、日志、文件和环境变量。

### 3. 状态机

```text
ONLINE
  │ 60 秒无心跳
  ▼
OFFLINE ──推送离线──▶
  │ 收到心跳
  ▼
RECOVERING
  │ 稳定 30 秒
  ▼
ONLINE ──推送上线──▶
```

- 防抖期间不重复推送。
- 连接器每 10 秒心跳一次，presence 每 5 秒扫描一次超时状态。
- 同一状态重复变化只推送一次。
- 推送失败记录投递状态并有限重试。
- relay 重启后通过持久化 presence 状态恢复，避免重复轰炸。

presence 持久化边界：

- V1.0.5 不把 presence 写入 Regent 业务 MySQL，避免公网服务接触业务数据。
- `regent-relay` 继续保持仅依赖 JDK，在 `~/.regent-relay/presence/` 下保存加密快照。
- 快照只含主机状态、状态时间和最小推送订阅；原子写入、文件权限 `0600`，推送令牌使用 AES-GCM 加密。
- V1.0.5 只允许一个活动 relay 实例负责监测。多实例高可用需要外部协调和共享存储，另行评审。
- 本地 Regent 保存业务侧订阅事实，relay 副本只用于主机离线推送；解绑、切换账号或注销后同步删除。

### 4. 推送订阅隔离

`mobile_push_subscription` 必须绑定：

```text
user_id + installation_id + relay_instance_id
```

主机状态推送只发送给拥有该 host 订阅关系的账号安装实例。

## 五、文件上传

### 1. 上限

- 单份文档 25MB。
- 每任务最多 20 份文档。
- 分片 2MB。
- 分片请求超时 60 秒。
- 上传会话 24 小时过期。
- Nginx `client_max_body_size` 至少 32MB。
- relay 请求体上限继续至少 32MB。

### 2. 上传流程

```text
App 计算文件 SHA-256
  → 创建 uploadSession
  → 逐片上传 chunk
  → 服务端校验 chunkHash
  → 记录已完成分片
  → 全部分片完成后合并/校验
  → 绑定任务或写入文件库
```

### 3. 数据模型

`mobile_upload_session`：

- `id`
- `user_id`
- `installation_id`
- `target_type`：TASK_DOCUMENT / FILE_LIBRARY
- `target_id`
- `filename`
- `content_type`
- `size_bytes`
- `content_hash`
- `chunk_size`
- `chunk_count`
- `completed_count`
- `status`
- `expires_at`
- `created_at`
- `completed_at`

分片元数据可以存入 `mobile_upload_chunk`，临时文件落 `~/.regent/uploads/{sessionId}/`。

### 4. 幂等

- 同一分片重复上传返回已成功状态。
- 分片内容哈希不一致时拒绝并终止该片重试。
- 完整文件哈希不一致时不绑定任务，保留失败诊断。
- 上传失败不得在 `task_document` 或文件库留下半成品。

## 六、项目与执行电脑授权

### 1. 数据模型

新增 `execution_host_project`：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `host_device_id` | 执行电脑 |
| `project_id` | 项目 |
| `owner_id` | 账号，冗余用于索引与校验 |
| `status` | PENDING/AVAILABLE/UNAVAILABLE/REVOKED |
| `last_verified_at` | 最后验证时间 |
| `failure_code` | 路径不存在、Codex 不可用等 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

唯一键：`host_device_id + project_id`。

### 2. 授权流程

```text
管理员/账号用户在电脑端选择项目
  → 设备代理检查项目目录和 Codex
  → 成功后写入 AVAILABLE
  → 手机只展示 AVAILABLE 且在线的主机
```

项目路径不返回手机。

### 3. 派发规则

- 任务创建时可以选择授权主机。
- 如果没有授权主机，可加入队列，状态为等待兼容设备。
- 派发时服务端再次校验账号、项目、主机授权和健康状态。
- 设备认领只返回自己拥有 `AVAILABLE` 授权的项目。
- 授权撤销后，设备立即不能认领该项目新任务。

## 七、设备配对

新增 `device_pairing_code`：

- `code`
- `owner_id`
- `device_id`
- `installation_id`
- `expires_at`
- `used_at`
- `confirmed_at`
- `status`

流程：

1. 电脑生成二维码。
2. 手机扫码。
3. 服务端把配对请求挂起为 `WAITING_CONFIRMATION`。
4. 电脑端显示手机名并要求确认。
5. 电脑确认后生成设备凭据。
6. 手机刷新绑定结果。

配对码只显示一次，电脑确认前不能建立设备访问。

## 八、设备撤销

执行电脑撤销必须在一个事务内：

1. 撤销设备凭据。
2. 停止设备心跳和派发。
3. 将所有活动 `task_run` 收敛为 `INTERRUPTED`。
4. 将相关任务迁到 `CANCELLED`。
5. 记录撤销操作者和原因。
6. 推送设备与任务状态变化。

不允许自动把任务重新派发到另一台电脑，避免重复修改工作区。

## 九、幂等模型

新增 `mobile_idempotency_key`：

- `user_id`
- `installation_id`
- `client_request_id`
- `operation`
- `resource_id`
- `response_status`
- `response_json`
- `request_hash`
- `created_at`
- `expires_at`

唯一键：`user_id + client_request_id`。

相同请求 ID 但 `request_hash` 不同时返回冲突，禁止复用旧动作结果。

覆盖动作：

- 新建任务
- 立即派发
- 加入队列
- 批准决策
- 驳回决策
- 停止任务
- 重试任务
- 撤销执行电脑

## 十、推送

### 1. 端口

核心域只定义 `PushNotificationSender` 端口：

```text
PushNotificationSender
  ├── ApnsPushSender
  ├── FcmPushSender
  └── DomesticVendorPushSender
```

推送通道类型和厂商响应只存在于 infrastructure。

### 2. 职责

- 本地 Regent：业务事件推送。
- 公网 presence：主机在线/离线推送。
- App：展示通知、深链和通知中心。

### 3. 深链

- 只传不透明引用，不传 token、任务正文和项目路径。
- 打开后校验登录态和资源归属。
- 资源不存在或跨账号统一显示“内容不存在或已失效”。

## 十二、移动端工程

### 1. 目录建议

```text
regent-mobile/
├── src/
│   ├── api/
│   ├── components/
│   ├── composables/
│   ├── pages/
│   ├── stores/
│   ├── native/
│   └── styles/
├── android/
├── ios/
└── capacitor.config.ts
```

### 2. 原生能力

- Keychain/Keystore 安全存储适配
- APNs/FCM/厂商推送适配
- `@capacitor/camera`
- 文件选择
- 深链
- 生物识别
- 网络安全状态
- App 更新提示

### 3. 本地数据

- 每个账号独立数据库或 store 命名空间。
- 草稿按 `installationId + userId` 隔离。
- 切换账号删除旧账号草稿、缓存和深链。
- 不在本地保存完整长期日志和敏感文档内容。

## 十三、数据库迁移建议

开发时以当时最新 Flyway 版本为准。P0 已落地：

- `V40__mobile_auth_session.sql`
- `V41__mobile_refresh_token_history.sql`

P1/P2 预计新增，执行前必须重新确认版本号：

- `execution_host_project`
- 推送订阅与 presence
- 移动端分片上传与幂等结果

约束：

- 不修改已执行的历史脚本。
- 所有表带账号隔离键或可通过项目/主机追溯账号。
- 推送令牌和设备凭据只保存哈希或加密值。
- 所有状态变更继续走领域方法。

## 十五、主要风险

| 风险 | 应对 |
|---|---|
| 公网中继从纯转发增加 presence 状态 | 只保存在线状态与订阅，不保存业务数据 |
| 厂商推送差异 | 推送适配层 + 真机矩阵 |
| iOS 后台限制 | APNs + 深链，不依赖后台轮询 |
| 文档上传慢 | 2MB 分片、断点续传、幂等 |
| 多账号串号 | 用户、安装、主机、项目、任务五层校验 |
| App Store 拒审 | 原生推送、生物识别、相机/文件、离线草稿 |
| 电脑休眠 | 主机守护 + 明确离线提示，不承诺关机执行 |
| relay 重启造成重复通知 | presence 状态持久化 + 去重窗口 |

## 十六、开发前置条件

以下条件不满足时，不进入正式 App 开发：

1. 公网 HTTPS 域名可用。
2. APNs 与 Android 推送供应商确定。
3. Apple Developer 账号和 Android 签名方案确定。
4. Nginx 和 relay 的 32MB 请求体配置完成。
5. A/B 双账号测试环境准备完成。
6. 一台电脑一个账号、项目与电脑授权规则确认。
7. presence 快照存储、加密密钥和单实例约束通过安全评审。
