# 需求澄清与任务拆解需求说明书

| 项目 | 内容 |
|---|---|
| 需求编号 | REG-V103-REQ |
| 优先级 | P0-3 |
| 文档版本 | v0.1 |
| 状态 | 待评审 |
| 编写日期 | 2026-10-20 |
| 依赖需求 | REG-V103-IA、REG-V103-CT |

## 一、背景与问题

Regent 的定位是多项目需求自动执行平台，但当前新建入口直接创建任务，用户仍需自己把需求转换成结构清晰的技术任务。

这种使用方式对用户要求过高：

1. 用户需要自己拆解工作范围。
2. 用户需要自己补充验收标准。
3. 用户需要判断任务之间是否存在依赖。
4. 用户需要自己发现需求中的歧义和遗漏。
5. 用户如果写得过于简略，Codex 只能自行猜测。
6. 一个需求分裂成多个任务后，平台没有统一视图展示整体进度。
7. 当前需求实体和“需求拆解为任务”的完整入口尚未开放，产品定位与用户实际使用方式不一致。

## 二、需求目标

### 1. 业务目标

- 让用户从“写技术任务”转为“提交业务需求”。
- 通过 AI 澄清减少需求遗漏和返工。
- 将一个需求稳定拆解为多个可独立执行和验收的任务。
- 建立任务到原需求的可追溯关系。
- 降低新用户编写高质量提示词的门槛。

### 2. 用户体验目标

- 用户可以用自然语言描述业务目标，不必了解 Codex 提示词结构。
- 系统最多追问少量关键问题，不能变成冗长问卷。
- 用户可以在创建前修改、删除、合并任务并调整依赖。
- AI 拆解结果应足够具体，避免只生成“分析需求”“完成开发”这类空任务。
- 所有任务必须有可验证的验收标准。

### 3. 非目标

- 不在 V1.0.3 自动派发拆解后的任务。
- 不在 V1.0.3 实现跨项目的大型需求协同。
- 不在 V1.0.3 自动生成完整产品方案、技术方案或排期。
- 不替代禅道、Jira 等外部需求管理系统。
- 不允许 AI 在未经用户确认的情况下直接创建任务。

## 三、用户与使用场景

### 1. 目标用户

| 用户 | 场景 |
|---|---|
| 产品经理 | 将业务需求拆成研发任务 |
| 项目负责人 | 提交一个跨多个模块的改动 |
| 开发人员 | 用更自然的方式描述复杂维护需求 |
| 测试人员 | 从需求和验收标准生成验证任务 |

### 2. 典型场景

示例需求：

> 部署和环境现在只能关联一个项目，希望能同时归属多个项目，并且在项目切换后能正确筛选。

系统应能：

- 识别这是“部署、环境、多项目关联、列表筛选”的复合需求。
- 追问数据库兼容、编辑行为和执行时项目选择等关键问题。
- 拆成数据模型、后端接口、部署表单、环境表单、列表筛选、测试验证等任务。
- 为每个任务提供验收标准。

## 四、核心概念

### 1. 需求

需求描述一个用户想达成的业务结果，可以关联多个任务。

需求不直接进入执行队列，只有拆解出的任务可以执行。

### 2. 任务

任务是可以独立执行、阻塞、重试和验收的工作单元。

任务继续使用现有任务状态机、决策分级和执行控制塔能力。

### 3. 需求拆解

由 AI 根据需求内容、项目资料和用户回答，生成建议任务列表。

拆解结果只是草稿，必须经过用户确认后才能创建任务。

### 4. 澄清问题

为消除需求中的关键歧义而提出的少量问题。

每个问题应提供：

- 为什么需要回答。
- 可选答案或建议默认值。
- 用户是否可以跳过。
- 跳过时系统采用的假设。

## 五、V1.0.3 范围

### 1. 支持的模式

任务页新建入口提供：

- 直接创建任务。
- 录入需求并拆解任务。

原有直接创建任务方式必须保留，不能强迫所有用户使用 AI 拆解。

### 2. 单项目限制

V1.0.3 一个需求只归属于一个主项目。

跨项目需求留到后续版本。

理由：

- 多项目需求会引入跨项目依赖、权限和计划协调。
- 首版先验证需求到任务的拆解质量。

### 3. 任务数量限制

一次拆解建议不超过 12 个任务。

超过时必须提示用户拆分为多个需求，避免生成无法管理的大批量任务。

### 4. 创建结果

用户确认后：

- 创建一条需求。
- 创建多个任务。
- 任务与需求建立关联。
- 任务默认为待执行，不自动派发。
- 用户可以选择立即派发其中部分任务。

## 六、需求生命周期

建议生命周期：

| 状态 | 含义 |
|---|---|
| 草稿 | 用户正在填写，尚未开始澄清 |
| 澄清中 | 系统正在提问或等待用户回答 |
| 待拆解 | 信息已足够，等待 AI 生成任务 |
| 待确认 | 已生成任务草稿，等待用户修改和确认 |
| 已计划 | 任务已经创建，尚未开始执行 |
| 执行中 | 至少一个关联任务正在执行 |
| 已完成 | 全部关联任务完成 |
| 部分完成 | 部分任务完成，部分失败或终止 |
| 已取消 | 用户取消需求 |

需求状态由关联任务状态和应用层编排推导，不允许前端直接设置。

## 七、业务流程

### 1. 完整流程

```text
新建需求
  → 填写目标、范围、约束和验收
  → AI 检查信息完整性
  → 用户回答最多 3 个关键问题
  → AI 生成任务拆解
  → 用户编辑、合并、删除、调整依赖
  → 用户确认
  → 事务性创建需求与任务
  → 需求详情展示任务整体进度
  → 用户手动派发任务
```

### 2. 信息已足够时

如果输入已经清楚，系统可以跳过提问，直接生成任务草稿。

不能为了固定流程强制用户回答无必要问题。

### 3. AI 调用失败时

用户可以：

- 重试澄清。
- 重试拆解。
- 切换为直接创建任务。
- 保留需求草稿稍后继续。

需求草稿不能因 AI 调用失败而丢失。

## 八、功能需求

### RD-01 新建方式选择

新建入口提供“直接创建任务”和“录入需求”两个明确选项。

要求：

- 不把两种方式隐藏在同一个模糊表单中。
- 用户选择后进入对应流程。
- 系统可以记住用户上一次选择，但首次不默认强制 AI 拆解。

### RD-02 需求基本信息

需求表单至少包含：

- 需求标题，必填。
- 所属项目，必填。
- 业务目标，必填。
- 背景和上下文，可选。
- 范围与非范围，可选。
- 约束条件，可选。
- 验收标准，可选但建议填写。
- 附件和截图，可选。

标题长度、正文长度和附件规则沿用现有任务的合理约束。

### RD-03 需求草稿自动保存

需求录入过程需要边写边保存。

要求：

- 按用户保存一份未提交需求草稿。
- 刷新、关闭弹框或重新登录后可恢复。
- 已确认创建后的草稿自动清理。
- 保存失败不打断输入，但需提示状态。

### RD-04 AI 完整性检查

AI 应根据以下维度判断信息是否足够：

- 目标是否明确。
- 影响对象是否明确。
- 改动边界是否明确。
- 是否需要兼容存量数据。
- 是否存在权限或安全风险。
- 验收方式是否可验证。

输出结构：

- `ready`：是否可以直接拆解。
- `questions`：需要澄清的问题，最多 3 个。
- `assumptions`：系统准备采用的默认假设。
- `risks`：已识别的高风险点。

### RD-05 澄清问题

规则：

- 每次最多展示 3 个问题。
- 每个问题必须说明为什么问。
- 可以提供建议答案，但不能替用户静默决定。
- 用户回答后，系统判断是否可以进入拆解。
- 用户跳过问题时，必须记录为假设并展示在拆解结果中。
- 不允许多轮无限追问；超过 3 个问题仍不清楚时，应建议用户补充正文或拆分需求。

V1.0.3 最多进行两轮澄清。

### RD-06 任务拆解

AI 返回任务草稿，每个任务包含：

- 临时任务编号。
- 标题。
- 目标。
- 工作范围。
- 非目标。
- 验收标准。
- 建议优先级。
- 依赖的临时任务编号。
- 建议决策等级或风险提示。
- 建议执行顺序。

必须拒绝以下结果：

- 空标题。
- 没有目标。
- 没有验收标准。
- 任务数量超过 12。
- 依赖关系成环。
- 引用不存在的任务编号。
- 重复或明显同义任务。

### RD-07 拆解结果编辑

用户可以：

- 修改任务标题、说明和验收标准。
- 删除任务。
- 合并两个任务。
- 调整任务顺序。
- 添加新任务。
- 调整依赖。
- 调整优先级。

所有修改只作用于草稿，确认前不得创建正式任务。

### RD-08 依赖关系

支持任务之间形成有向无环图。

规则：

- 被依赖任务未完成时，依赖任务不能进入执行位。
- 依赖关系不能成环。
- 删除任务时，系统必须提示如何处理引用它的依赖。
- V1.0.3 不要求支持跨项目依赖。

### RD-09 创建前确认

用户点击“创建需求和任务”前，系统展示：

- 需求名称。
- 所属项目。
- 任务总数。
- 有依赖的任务数量。
- 被跳过的澄清问题和系统假设。
- 高风险任务提示。

用户必须勾选或明确点击确认。

### RD-10 事务性创建

用户确认后，系统必须一次性创建需求和全部任务。

失败时：

- 不允许只创建需求或只创建部分任务。
- 已保存的拆解草稿必须保留。
- 用户可以修正后重试。

### RD-11 立即派发

创建成功后，用户可以选择：

- 暂不派发。
- 派发无前置依赖的任务。
- 选择部分任务立即派发。

依赖未完成的任务即使被选择，也只能进入排队或等待状态，不能绕过依赖。

### RD-12 需求详情

需求详情至少展示：

- 需求标题和目标。
- 需求状态。
- 所属项目。
- 原始描述。
- 系统假设和澄清记录。
- 关联任务列表。
- 任务依赖关系。
- 整体进度。
- 待决策事项。
- 失败任务。
- 关联缺陷。
- 执行记录入口。

### RD-13 任务追溯

每个由需求拆解出的任务必须显示所属需求。

用户可以从任务详情跳转到需求详情，也可以从需求详情打开任务。

### RD-14 需求状态推导

需求状态根据关联任务计算：

- 全部任务完成：已完成。
- 全部任务取消：已取消。
- 至少一个任务完成且其余失败或取消：部分完成。
- 至少一个任务执行中或排队中：执行中。
- 全部任务待执行：已计划。
- 没有任务且尚未确认：待确认或澄清中。

不能由用户直接修改需求执行状态。

### RD-15 AI 调用与失败恢复

AI 调用必须记录：

- 调用阶段。
- 使用的项目。
- 请求标识。
- 开始和结束时间。
- 结果状态。
- 失败原因摘要。

AI 失败不能导致需求草稿或已经修改的任务草稿丢失。

### RD-16 敏感信息处理

- 需求正文、附件和 AI 输出必须按当前用户隔离。
- 诊断和日志中不能记录完整敏感正文。
- 图片附件继续使用现有上传和鉴权机制。
- AI 上下文只能包含用户有权访问的项目和资料。

## 九、页面与交互

### 1. 新建方式

新建弹框第一步：

- `直接创建任务`：进入现有任务表单。
- `录入需求`：进入需求表单。

使用简短说明区分两者，但不在页面堆叠大段教程。

### 2. 需求录入

页面分为：

1. 需求基本信息。
2. 目标、范围和约束。
3. 验收标准。
4. 附件。
5. “检查并拆解”操作。

用户可以随时保存并退出。

### 3. 澄清步骤

展示：

- 当前识别到的需求摘要。
- 最多 3 个问题。
- 每个问题的建议答案。
- “使用建议假设并继续”入口。

用户不应被困在必须回答所有问题的流程里。

### 4. 任务草稿

采用可编辑列表，不使用只读长文本。

每个任务卡片展示：

- 标题。
- 目标。
- 验收标准。
- 依赖。
- 风险。
- 编辑和删除操作。

页面顶部显示任务数量、依赖数量和风险数量。

### 5. 创建确认

确认区域固定展示：

- 将创建的正式对象数量。
- 被采纳的 AI 假设。
- 无法自动验证的验收标准。
- 高风险提示。

主要按钮为“创建需求和任务”。

## 十、业务规则

1. 需求必须属于一个真实且用户有权访问的项目。
2. 需求创建后可以直接修改文字，但不能绕过任务状态重新计算需求状态。
3. 任务只能在用户确认后创建。
4. 所有任务必须有至少一条验收标准。
5. AI 生成的临时编号只用于本次草稿，不进入正式任务号。
6. 合并任务后，原依赖必须迁移到保留任务。
7. 删除任务前必须处理依赖引用。
8. 依赖关系不能形成环。
9. 已创建任务不能通过修改拆解草稿被静默删除。
10. 一个需求最多关联 12 个 V1.0.3 任务。

## 十一、AI 输出约束

AI 拆解结果应使用结构化数据，不接受无法解析的自由文本。

最低结构：

```json
{
  "summary": "需求摘要",
  "assumptions": ["假设"],
  "tasks": [
    {
      "key": "T1",
      "title": "任务标题",
      "objective": "任务目标",
      "scope": ["范围"],
      "outOfScope": ["非目标"],
      "acceptanceCriteria": ["验收标准"],
      "dependencies": [],
      "priority": 2,
      "risk": "L1",
      "suggestedOrder": 1
    }
  ]
}
```

服务端必须校验结构、数量、依赖和必填字段后才能展示给用户。

## 十二、非功能需求

### 1. 性能

- 需求草稿保存不阻塞输入。
- 单次澄清请求在合理超时内返回。
- 拆解请求有明确进度和停止入口。
- 任务草稿编辑不因任务数量正常增加而卡顿。

### 2. 可靠性

- 草稿自动保存失败不能丢失当前内存内容。
- AI 请求重复提交必须幂等。
- 用户连续点击确认不能重复创建需求或任务。
- 创建过程失败必须整体回滚。

### 3. 可解释性

- 展示 AI 采用了哪些假设。
- 说明哪些问题是用户跳过而不是系统确定。
- 高风险建议需要说明原因。

### 4. 安全

- 不同账号之间不能读取需求和草稿。
- AI 只接收当前用户有权访问的项目资料。
- 日志和监控不得记录完整需求正文。

## 十三、验收场景

### 场景 1：需求信息完整

**Given** 用户输入了明确目标、范围和验收标准  
**When** 点击检查并拆解  
**Then** 系统可以跳过提问并直接生成任务草稿

### 场景 2：需求存在歧义

**Given** 用户没有说明是否需要兼容存量数据  
**When** 系统检查需求  
**Then** 最多提出 3 个关键问题  
**And** 每个问题说明询问原因和建议答案

### 场景 3：用户跳过问题

**Given** 用户选择跳过澄清问题  
**When** 生成拆解结果  
**Then** 系统展示采用的假设  
**And** 用户确认前可以修改

### 场景 4：编辑任务草稿

**Given** AI 生成了 5 个任务  
**When** 用户合并其中两个任务  
**Then** 原依赖自动迁移到保留任务  
**And** 依赖关系仍然无环

### 场景 5：依赖成环

**Given** 用户调整依赖导致 T1 依赖 T2，T2 又依赖 T1  
**When** 用户尝试确认  
**Then** 系统阻止创建并指出循环依赖

### 场景 6：确认创建

**Given** 用户确认了包含 4 个任务的需求  
**When** 点击创建  
**Then** 创建 1 条需求和 4 条任务  
**And** 每条任务都能跳转回需求

### 场景 7：中途失败

**Given** 创建第 3 个任务时数据库失败  
**When** 系统返回  
**Then** 需求和前两个任务都不能残留  
**And** 用户的任务草稿仍然存在

### 场景 8：页面刷新

**Given** 用户已经填写需求并完成第一轮澄清  
**When** 刷新页面  
**Then** 需求内容、澄清记录和已生成草稿可以恢复

### 场景 9：切换回直接任务

**Given** AI 拆解多次失败  
**When** 用户选择“改为直接创建任务”  
**Then** 当前需求正文可以作为任务描述带入  
**And** 不丢失已填写的附件

### 场景 10：创建后派发

**Given** 需求创建了 3 个任务，其中 T2 依赖 T1  
**When** 用户选择全部立即派发  
**Then** T1 进入可执行状态  
**And** T2 不能绕过 T1 的依赖直接执行

## 十四、成功指标

| 指标 | 说明 |
|---|---|
| 需求拆解采纳率 | AI 结果经少量修改后即可创建的比例 |
| 任务重写率 | 用户删除并重新创建大部分任务的比例 |
| 澄清问题有效率 | 用户实际回答且改变拆解结果的问题比例 |
| 首次创建成功时间 | 从进入需求流程到创建任务的耗时 |
| 创建后返工率 | 创建后短时间内大幅修改任务的比例 |
| 直接任务回退率 | 用户放弃需求拆解转为直接任务的比例 |
| 验收标准覆盖率 | 创建任务中包含可验证验收标准的比例 |

## 十五、风险与待确认项

| 风险或问题 | 影响 | 建议 |
|---|---|---|
| AI 拆解出空泛任务 | 用户不信任 | 服务端强制目标、范围和验收字段质量校验 |
| 澄清问题过多 | 用户中途退出 | 每次最多 3 个，最多两轮 |
| 用户需求本身就是跨项目 | 无法完整拆解 | V1.0.3 明确限制单项目，提示拆分为多个需求 |
| 重复提交导致重复创建 | 数据污染 | 请求幂等和前端按钮守卫 |
| 历史任务修改影响需求状态 | 状态不一致 | 由统一应用服务根据任务实时推导 |
| AI 输出不稳定 | 页面解析失败 | 结构化输出、服务端校验和可重试 |
| 与外部需求系统的编号冲突 | 后续迁移困难 | 正式需求使用平台内部 ID，外部编号做映射字段 |
