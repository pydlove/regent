## 一、版本定位

V1.0.3 不继续扩充功能数量，而是解决当前产品最影响使用和信任的三类问题：

1. 用户找不到功能，首次使用路径过长。
2. 任务执行过程不透明，用户不知道任务为什么没开始、是否卡住、失败后该怎么办。
3. 用户仍然需要自己写完整技术任务，无法直接提交需求并由平台完成澄清和拆解。

因此 V1.0.3 的主题是：

> **让用户找得到、敢托管、会表达。**

## 二、本版本范围

V1.0.3 只规划以下三个需求，不并行扩展其他产品能力。

| 优先级 | 需求编号 | 名称 | 解决的问题 |
|---|---|---|---|
| P0-1 | REG-V103-IA | 信息架构收敛与首启引导 | 菜单过多、入口分散、新用户不知道先做什么 |
| P0-2 | REG-V103-CT | 执行控制塔 | 执行不可见、状态解释不清、失败无法定位和恢复 |
| P0-3 | REG-V103-REQ | 需求澄清与任务拆解 | 用户必须自己写技术提示词，需求无法直接转成任务 |

## 三、需求之间的依赖关系

```text
信息架构收敛
    │
    ├── 提供统一的工作台主入口
    ├── 提供全局待办入口
    └── 提供任务页内的需求录入入口
             │
             ▼
        执行控制塔
             │
             └── 统一展示任务、部署、测试执行

需求澄清与任务拆解
    │
    └── 创建出的任务直接进入执行控制塔和现有任务流程
```

执行顺序建议：

1. 先确定菜单、路由、工作台和全局待办的信息架构。
2. 再在已经确定的工作台结构内实现执行控制塔。
3. 最后在任务页实现需求澄清、拆解和批量创建任务。

如果把顺序反过来，执行控制塔或需求拆解会继续增加新入口，导致信息架构再次失控。

## 四、共同产品原则

### 1. 新能力不默认新增一级菜单

新增功能先判断它属于哪个用户主流程：

- 新主流程：才允许进入一级菜单。
- 已存在流程中的对象：放入页签或列表。
- 单个动作：放入工具栏、详情侧栏或命令入口。

### 2. 页面优先回答用户的问题

页面首屏必须优先展示：

- 现在发生了什么。
- 为什么没有继续。
- 需要用户做什么。
- 用户下一步可以执行什么操作。

统计图表不能替代可操作的业务信息。

### 3. 原始技术信息按需展开

默认使用用户能理解的语言展示阶段、结果和错误。

命令、JSONL、完整日志和技术事件保留，但默认折叠在“技术详情”中。

### 4. 所有高风险动作必须有守卫和审计

停止、重试、重新排队、更换设备、发布等操作必须：

- 执行前校验对象状态。
- 在必要时二次确认。
- 记录操作者、时间和操作结果。

### 5. 兼容现有数据和链接

信息架构调整不能删除现有业务数据。

旧路由必须重定向到新位置，已有收藏和通知深链不能失效。

## 五、本版本明确不做

- 决策中心整体重构。
- 多级发布审批和一键回滚。
- GitLab、禅道、飞书、企微集成。
- 团队 RBAC、项目成员和审批代理。
- Token 预算、成本中心和组织级容量管理。
- 插件市场、多模型自由切换。
- 仅以视觉优化为目的的大屏或统计卡片改造。

这些需求可以进入后续版本，但不能挤占 V1.0.3 的三项核心范围。

## 六、版本成功指标

### 北极星指标

**无需人工干预完成并验收的任务比例。**

### 配套指标

| 指标 | 说明 |
|---|---|
| 首次创建任务耗时 | 新用户从进入系统到成功创建第一个任务的时间 |
| 功能查找成功率 | 用户在无帮助情况下完成目标操作的比例 |
| 执行异常定位时间 | 从发现问题到确认原因的时间 |
| 原始日志查看率 | 在未查看原始 JSON/日志的情况下解决执行问题的比例 |
| 需求拆解采纳率 | AI 拆解任务经少量修改后即可创建的比例 |
| 需求重写率 | 用户放弃 AI 结果并重新录入的比例 |

具体目标值在上线前根据当前真实数据建立基线后确定，不以“页面数量”或“功能数量”衡量版本成功。

## 七、评审时需要确认的事项

1. 一级菜单是否最终确定为“工作台、任务、交付、项目”。
2. 决策是否彻底取消一级菜单，只保留全局待办和工作台入口。
3. 执行控制塔是否覆盖测试执行，还是 V1.0.3 只覆盖任务和部署。
4. 需求拆解是否限制为单项目需求。
5. 首启引导是否按账号只展示一次，还是允许重新进入。
