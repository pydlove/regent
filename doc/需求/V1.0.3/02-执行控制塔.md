| 项目 | 内容 |
|---|---|
| 需求编号 | REG-V103-CT |
| 优先级 | P0-2 |
| 文档版本 | v0.1 |
| 状态 | 待评审 |
| 编写日期 | 2026-10-20 |
| 依赖需求 | REG-V103-IA |

## 一、背景与问题

Regent 已经支持任务执行、部署执行和测试执行，但执行信息分散在任务详情、部署日志、测试结果和设备设置中。用户只能看到“排队中”“运行中”或“失败”等最终概括，很难判断执行系统内部到底发生了什么。

当前主要问题：

1. 任务显示待执行时，用户不知道是在等待并发位、等待设备、等待依赖，还是尚未派发。
2. 任务显示运行中但长时间没有输出时，用户无法区分模型思考、网络阻塞、设备失联和进程退出。
3. 失败后只看到错误文本，缺少最后成功阶段、失败分类和下一步建议。
4. 一个任务多次重试后，用户无法快速看出每次尝试的设备、会话和结果差异。
5. 部署和测试执行各有自己的日志，无法使用统一方式判断运行状态。
6. 设备离线、Codex 不可用和工作区不存在等问题，经常在任务已经派发后才暴露。
7. 用户排障需要手工收集任务号、执行号、设备、Codex 版本和工作区信息。

## 二、需求定义

执行控制塔是面向所有执行行为的统一可观测与控制能力。

它不是一个独立的新菜单，也不是原始日志集合，而是统一回答五个问题：

1. 现在有哪些任务、部署或测试正在执行？
2. 它在哪台设备、哪个工作区、执行到哪个阶段？
3. 它是在正常运行、等待模型、等待人工、等待执行位，还是已经失联？
4. 为什么没有继续，下一步该由谁处理？
5. 用户可以重试、继续、停止、重新排队还是更换设备？

## 三、需求目标

### 1. 业务目标

- 降低执行异常导致的人工支持和排障成本。
- 提高用户对自动执行的信任度。
- 提高中断、失败和等待场景的恢复成功率。
- 为任务、部署和测试提供统一的执行状态语言。
- 为后续自动诊断、容量分析和智能调度提供稳定的事件基础。

### 2. 用户体验目标

- 用户在 10 秒内判断一个任务为什么没有开始。
- 用户无需查看原始 JSON 或完整日志即可理解大多数执行状态。
- 心跳中断后 30 秒内能在界面看到异常状态。
- 失败后能立即看到最后成功阶段、失败阶段和建议操作。
- 用户可以一键复制或导出脱敏后的诊断信息。

### 3. 非目标

- 不替代任务、部署和测试各自的业务详情页。
- 不在 V1.0.3 实现 AI 自动修复所有失败。
- 不预测任务准确完成时间。
- 不实现任意阶段回滚。
- 不实现跨地域或跨集群自动调度。
- 不重构现有任务状态机。

## 四、核心产品模型

### 1. 执行对象

执行控制塔统一管理以下执行：

- 任务运行：一次 Codex 任务尝试。
- 部署运行：一次部署执行。
- 测试运行：一次测试用例执行。

同一业务对象可能拥有多次执行记录，因此控制塔必须展示“本次执行”，不能只展示业务对象。

### 2. 双状态模型

每个执行同时具备业务状态和健康状态。

#### 业务状态

| 状态 | 含义 |
|---|---|
| 等待调度 | 已提交，尚未进入执行队列或尚未派发 |
| 排队中 | 等待执行位、设备或前置条件 |
| 已分配 | 已找到执行设备，尚未开始实际工作 |
| 执行中 | 正在运行任务、部署或测试 |
| 等待决策 | 执行暂停，等待人工批准或驳回 |
| 验证中 | 执行完成主要动作，正在运行测试或验收 |
| 交付中 | 正在发布、上传或重启服务 |
| 已完成 | 执行成功结束 |
| 失败 | 执行以失败结束 |
| 已终止 | 用户停止或平台中断 |

#### 健康状态

| 状态 | 含义 |
|---|---|
| 正常 | 有心跳或近期活动，状态推进符合预期 |
| 缓慢 | 长时间没有新事件，但仍有设备或进程心跳 |
| 疑似卡住 | 超过阈值没有进展，需要提示用户 |
| 设备失联 | 心跳或租约中断 |
| 状态未知 | 无法获得足够的执行信息 |

业务状态和健康状态必须独立展示。

例如：

- `执行中 + 正常`：正常推进。
- `执行中 + 缓慢`：模型或命令长时间未返回。
- `执行中 + 设备失联`：任务记录仍在运行，但执行设备已经无法联系。
- `排队中 + 正常`：等待执行位属于正常排队。

### 3. 统一执行阶段

执行过程映射为以下阶段：

1. 已创建。
2. 等待执行位。
3. 等待执行设备。
4. 分配设备。
5. 准备工作区。
6. 初始化 Codex 或执行脚本。
7. 分析或执行。
8. 等待决策。
9. 修改文件或产生变更。
10. 运行测试与验收。
11. 构建与部署。
12. 健康检查。
13. 完成或失败。

不是每种执行都会经过全部阶段，但阶段命名和含义必须统一。

### 4. 心跳与进度

执行记录必须包含：

- 当前阶段。
- 最后事件时间。
- 最后心跳时间。
- 当前设备。
- 当前工作区。
- 当前进程或会话。
- 阶段开始时间。

建议默认阈值：

- 15 秒无心跳：健康状态转为“缓慢”。
- 30 秒无心跳：健康状态转为“疑似卡住”并产生提示。
- 设备租约到期：健康状态转为“设备失联”。

阈值最终应可配置，但 V1.0.3 可以先使用系统默认值。

## 五、入口与页面设计

### 1. 主入口

执行控制塔不新增一级菜单。

主要入口：

- 工作台首屏的执行控制塔区域。
- 顶栏运行状态入口。
- 任务页“执行中”和“异常”视图。
- 交付页的测试和部署执行。
- 通知和待办深链。

### 2. 工作台总览

工作台顶部显示紧凑状态栏：

`执行中 3/5 · 排队 2 · 待决策 1 · 异常 1`

下方展示实时执行列表。

默认排序：

1. 设备失联和疑似卡住。
2. 失败且需要处理。
3. 待决策。
4. 执行中。
5. 排队中。
6. 已完成记录。

用户可切换排序和筛选，但明确异常优先。

### 3. 执行列表字段

每条执行记录至少展示：

- 名称。
- 类型：任务、部署或测试。
- 项目。
- 当前阶段。
- 业务状态。
- 健康状态。
- 当前设备。
- 已运行时长。
- 最后活动时间。
- 阻塞原因摘要。
- 主要操作。

### 4. 执行详情

执行详情采用侧栏或详情页，必须包含：

#### 顶部摘要

- 名称和类型。
- 当前阶段。
- 业务状态。
- 健康状态。
- 已运行时长。
- 最后活动时间。

#### 执行上下文

- 项目。
- 工作区。
- 执行设备。
- 设备在线状态。
- Codex 版本和路径。
- 客户端壳和 Runtime 版本。
- Codex 会话 ID。
- 执行 ID 和尝试次数。
- 触发人和触发来源。

#### 可读时间线

- 按时间展示阶段变化和关键事件。
- 默认隐藏重复的技术心跳。
- 文件修改、命令执行、等待决策等关键事件必须展示。
- 支持查看某条事件的详细信息。

#### 操作区

- 根据状态展示允许的操作。
- 危险操作与普通操作视觉区分。
- 操作后立即刷新详情。

#### 技术详情

- 原始事件。
- 原始日志。
- 完整命令。
- JSONL 消息。
- 配置快照。

默认折叠。

## 六、功能需求

### CT-01 统一执行列表

系统应提供任务、部署、测试的统一执行列表。

支持按以下条件筛选：

- 执行类型。
- 项目。
- 业务状态。
- 健康状态。
- 执行设备。
- 时间范围。
- 关键词。

分页和实时刷新不能导致当前选中记录丢失。

### CT-02 排队原因解释

排队中的执行必须展示明确原因：

- 等待全局执行位。
- 等待可用执行设备。
- 设备上 Codex 不可用。
- 等待前置任务或依赖。
- 失败冷却中。
- 等待用户派发。
- 工作区不满足执行条件。

无法判断原因时显示“正在确认排队原因”，不能只显示“排队中”。

### CT-03 设备与执行上下文

执行详情必须展示执行设备和工作区。

设备信息包括：

- 设备名称。
- 在线状态。
- 最后心跳时间。
- Codex 是否可用。
- Codex 路径和版本。
- 客户端壳与 Runtime 版本。

工作区信息包括：

- 项目名称。
- 工作区路径。
- 是否为 Git 工作区。
- 当前分支或提交。
- 是否存在未提交变更。

敏感路径可以按账号和角色做脱敏，V1.0.3 默认保留完整路径供本人排障。

### CT-04 心跳与卡住检测

系统应记录执行心跳，并根据阈值计算健康状态。

规则：

- 有持续心跳但没有业务进展时，显示“等待模型响应”或“命令执行中”。
- 心跳变旧时显示“缓慢”。
- 超过卡住阈值时显示“疑似卡住”，并给出最后阶段和最后事件。
- 设备失联时显示“设备失联”，不能继续显示为正常执行。
- 恢复心跳后健康状态可自动恢复正常，但必须保留异常历史。

### CT-05 用户可读时间线

时间线必须将技术事件转换为用户可理解的阶段和动作。

示例：

- “已分配给 MacBook Pro 本机设备”。
- “正在准备工作区”。
- “Codex 会话已创建”。
- “正在分析项目结构”。
- “修改了 4 个文件”。
- “正在运行类型检查”。
- “需要 L2 人工决策”。
- “部署脚本已上传”。
- “健康检查通过”。

重复事件应合并展示，避免时间线被心跳和空日志刷屏。

### CT-06 失败归因

失败的执行必须给出一个主分类。

V1.0.3 分类：

| 分类 | 示例 |
|---|---|
| 设备不可用 | 设备离线、租约失效、代理未运行 |
| Codex 不可用 | 未安装、路径错误、版本不可执行 |
| 身份或模型异常 | 未登录、Token 失效、模型服务错误 |
| 网络异常 | 无法连接执行服务、代理中断 |
| 工作区异常 | 路径不存在、权限不足、Git 状态冲突 |
| 命令或脚本失败 | 构建、测试、部署脚本退出码非 0 |
| 配置异常 | 缺少服务器、环境变量或必要凭据 |
| 部署异常 | SSH、上传、重启或健康检查失败 |
| 人工决策 | 用户驳回、需要更多信息 |
| 用户终止 | 用户主动停止 |
| 平台中断 | 平台重启或执行进程丢失 |
| 未知异常 | 无法可靠分类，需要查看诊断包 |

主分类之外可以保留原始错误摘要，但不得用原始摘要替代分类。

### CT-07 下一步建议

失败或阻塞时，系统应根据分类展示建议。

示例：

- 设备离线：检查设备、重新连接或更换设备。
- Codex 不可用：打开执行设置并重新检测。
- 工作区不存在：检查项目路径。
- 脚本失败：查看失败命令和最后成功阶段。
- 设备失联：等待租约回收或重新排队。
- 待决策：打开决策详情。

建议必须指向可执行入口，不能只显示一段说明文字。

### CT-08 执行操作

V1.0.3 支持以下操作，具体可用性由业务状态决定：

| 操作 | 可用条件 | 结果 |
|---|---|---|
| 派发 | 待执行且未派发 | 进入排队或执行 |
| 重试 | 失败或已终止 | 创建新的执行尝试 |
| 恢复会话 | 存在可用 Codex 会话且状态允许 | 从原会话继续 |
| 重新排队 | 失联、平台中断或可重试状态 | 任务重新进入队列 |
| 停止 | 执行中、排队中或部署中 | 终止当前执行 |
| 更换设备 | 尚未产生不可迁移状态 | 任务在目标设备重新开始 |
| 打开详情 | 任意状态 | 进入业务对象详情 |

操作约束：

- 不允许对已完成执行重试。
- 不允许对正在运行执行重复派发。
- 停止操作必须幂等。
- 用户操作必须记录审计信息。
- 更换设备前必须提示未提交文件和会话迁移风险。

### CT-09 执行诊断包

系统应支持一键导出诊断包。

内容至少包括：

- 业务对象名称和 ID。
- 执行 ID。
- 项目和工作区路径。
- 执行设备、Codex、Shell、Runtime 信息。
- 当前业务状态和健康状态。
- 失败分类。
- 最近阶段时间线。
- 最近 200 条技术事件。
- 脱敏后的关键配置摘要。

禁止包含：

- 登录 Cookie。
- API Token。
- SSH 密码。
- 环境变量中的密码和密钥。
- 用户上传附件正文。

导出前应展示包含内容摘要。

### CT-10 通知与深链

以下情况应产生通知：

- 执行失败。
- 疑似卡住。
- 设备失联。
- 等待人工决策。
- 长时间排队。
- 用户操作未能生效。

通知必须包含：

- 任务或部署名称。
- 当前阶段。
- 原因摘要。
- 打开执行详情的深链。

同一执行重复异常不能无限发送相同通知。

### CT-11 执行历史

业务对象详情中应保留全部执行尝试。

每次尝试展示：

- 尝试序号。
- 设备。
- 开始和结束时间。
- 结果。
- 失败分类。
- Codex 会话。

用户可以对比相邻两次尝试，定位环境或版本变化。

### CT-12 状态恢复

平台重启、设备恢复或网络恢复后，控制塔必须刷新真实状态。

规则：

- 平台重启后，原进程不能长期显示运行中。
- 设备重新上线后，系统重新计算可执行状态。
- 失联执行回收后，业务状态和健康状态同步更新。
- 刷新页面不能丢失当前筛选和详情位置。

### CT-13 原始技术详情

原始事件和日志必须可在执行详情中查看。

要求：

- 默认折叠。
- 支持复制。
- 支持按调试级别筛选。
- 自动高亮错误、超时和退出码。
- 不得暴露密码和认证信息。

### CT-14 审计

以下操作必须写入审计记录：

- 重试。
- 恢复会话。
- 重新排队。
- 停止。
- 更换设备。
- 导出诊断包。

审计记录包含操作者、时间、执行 ID、操作前后状态和结果。

## 七、页面状态与空态

### 1. 无执行

展示“当前没有正在执行的记录”，并提供进入任务或交付页的主要操作。

### 2. 只有排队

明确说明排队是正常状态，并展示最早等待时间和主要原因。

### 3. 数据加载失败

保留上一次成功数据，提示“状态刷新失败”，提供重新加载。

不能把接口失败误显示成设备离线。

### 4. 状态未知

显示“状态未知”并说明缺少心跳或事件，不猜测执行结果。

## 八、权限与安全

- 用户只能查看自己账号下项目的执行。
- 诊断包必须经过统一脱敏。
- 原始日志中的密码、Token、Cookie 和密钥必须过滤。
- 所有写操作必须通过业务应用服务执行，不允许前端直接修改状态。
- 深链需要继续使用现有登录和归属校验。

## 九、非功能需求

### 1. 实时性

- 活跃执行状态在正常情况下 5 秒内更新到界面。
- 卡住或失联状态在阈值触发后 30 秒内可发现。
- 支持轮询或流式推送，但前端必须提供降级方式。

### 2. 性能

- 执行列表首屏在正常数据量下 2 秒内可用。
- 实时刷新不能导致列表闪烁和滚动位置重置。
- 历史事件较多的执行详情应采用渐进加载。

### 3. 稳定性

- 单个执行记录解析失败不能拖垮整个列表。
- 原始事件格式异常时应显示可读错误，不返回空页面。
- 控制塔故障不能阻止任务页和部署页执行原有操作。

### 4. 可维护性

- 三种执行类型应映射到统一执行视图。
- 不允许为任务、部署和测试分别复制三套状态组件。
- 状态名称、阶段和失败分类必须集中定义。

## 十、验收场景

### 场景 1：等待执行位

**Given** 全局并发上限已满，任务处于排队中  
**When** 用户打开工作台执行控制塔  
**Then** 该任务显示“等待全局执行位”  
**And** 展示当前使用数和上限

### 场景 2：运行中但无新日志

**Given** 执行设备仍有心跳，但 Codex 超过一段时间没有业务输出  
**When** 用户查看执行详情  
**Then** 健康状态显示“缓慢”或“疑似卡住”  
**And** 页面说明最后一次活动和最后阶段

### 场景 3：设备失联

**Given** 执行中的设备停止心跳  
**When** 超过失联阈值  
**Then** 执行健康状态变为“设备失联”  
**And** 通知用户并提供重新排队或更换设备入口

### 场景 4：执行失败

**Given** 部署脚本以非 0 退出码结束  
**When** 用户打开执行详情  
**Then** 显示主分类“命令或脚本失败”  
**And** 展示最后成功阶段、失败命令和日志位置  
**And** 提供重试或查看部署详情操作

### 场景 5：平台重启

**Given** 平台重启时存在运行中的任务  
**When** 用户重新进入控制塔  
**Then** 旧进程显示为已中断或重新排队  
**And** 不再长期显示为正常执行中

### 场景 6：导出诊断包

**Given** 用户打开失败执行详情  
**When** 点击导出诊断包  
**Then** 系统生成包含执行摘要和最近事件的压缩包  
**And** 其中不包含密码、Token 或 Cookie

### 场景 7：刷新页面

**Given** 用户正在查看某条执行详情  
**When** 页面刷新  
**Then** 用户仍停留在同一执行详情  
**And** 筛选条件保持

## 十一、成功指标

| 指标 | 说明 |
|---|---|
| 异常自动发现率 | 卡住和失联中由系统主动发现的比例 |
| 平均异常定位时间 | 从异常发生到用户确认原因的时间 |
| 原始日志查看率 | 不查看原始日志即可解决问题的比例 |
| 失败恢复成功率 | 重试或重新排队后成功的比例 |
| 排队原因解释率 | 排队记录中能展示明确原因的比例 |
| 诊断包使用率 | 排障过程中导出诊断包的比例 |
| 重复异常通知率 | 同一异常重复发送的通知数量 |

## 十二、风险与待确认项

| 风险或问题 | 影响 | 建议 |
|---|---|---|
| 任务、部署、测试底层事件结构不同 | 统一展示成本高 | 先定义稳定统一视图，不要求底层存储完全一致 |
| 心跳过频导致数据膨胀 | 存储和查询压力 | 心跳聚合展示，原始心跳按周期清理 |
| 卡住阈值不准确 | 误报或漏报 | V1.0.3 使用保守默认值并允许后续配置 |
| 更换设备可能丢失本地修改 | 数据风险 | 默认只允许未产生不可迁移变更时更换 |
| 诊断包含敏感信息 | 安全问题 | 统一脱敏服务和导出前检查 |
| 原始日志过多 | 前端卡顿 | 分页、虚拟滚动和渐进加载 |
| 与现有任务状态重复 | 用户 confusion | 明确区分“任务业务状态”和“本次执行健康状态” |
