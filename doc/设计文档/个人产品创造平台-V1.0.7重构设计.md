# Regent 个人产品创造平台 V1.0.7 重构设计

> 分支：`feature_V1.0.7_R100B001`
> 状态：设计稿
> 日期：2026-10-26
> 目标：把现有企业研发协作平台重构为面向非技术个人创作者的产品交付平台

## 一、结论先行

Regent 不再把目标用户定义为“个人开发者”，而是定义为：

> 有产品想法，但没有研发能力，希望自己拥有产品资产和运行环境的个人创业者、行业专家或独立创作者。

平台负责把想法变成可运行、可验收、可上线、可迭代的 Web 产品。用户负责业务判断、购买基础设施和完成授权，不负责理解技术框架、代码、分支、部署脚本和服务器配置。

一句话定位：

> 用户购买并拥有基础设施，Regent 负责产品设计、原型、开发、测试、上线和回滚。

MVP 的核心闭环固定为：

`想法 -> 产品方案 -> 可点击原型 -> AI 开发 -> 预览验收 -> 发布上线 -> 自然语言迭代 -> 版本回滚`

## 二、关键产品决策

### 2.1 保留现有代码基础

不在新分支重写所有系统。现有认证、账户隔离、AI 任务执行、运行记录、测试、Git 操作、部署连接、附件和通知能力继续作为底层支撑。

### 2.2 新增 `studio` 限界上下文

新的个人产品主流程放入 `studio` 上下文，不继续把产品概念硬塞进 `requirement`、`delivery`、`initiative` 和 `workflow_template`。

`studio` 负责：

- 产品与产品阶段
- 产品方案版本
- 原型版本和原型意见
- 产品变更请求
- 构建版本
- 环境资产
- 环境准备进度
- 发布版本
- 产品级用量

现有 `execution`、`testing`、`gitcommit` 和 `deployment` 作为内部引擎，通过端口被 `studio` 调用。

### 2.3 固定流程，不提供流程编辑器

个人创作者不需要配置研发流程。V1 固定为：

1. 产品方案
2. 原型确认
3. 构建与测试
4. 预览验收
5. 生产发布
6. 持续迭代

研发流程模板、阶段审批角色和门禁编辑器从消费者产品下线。

### 2.4 基础设施归用户

MVP 支持自带基础设施：

- 用户自己的 Git 私有仓库
- 用户自己的 Ubuntu 云服务器
- 后续支持用户自己的域名

平台只做教程引导、授权、检测和自动化，不替用户购买或持有资产。

### 2.5 Git 和分支对用户隐藏

用户只看到产品方案、原型、预览、版本和回滚。Git 分支、提交、合并和标签全部由平台自动管理，默认不显示技术细节。

## 三、目标用户与核心任务

### 3.1 目标用户

- 有明确业务想法，但不会开发
- 不懂技术框架、数据库、接口、性能、测试和部署
- 愿意购买云服务器和 Git 账号
- 能按图文教程完成注册、购买和授权
- 希望产品资产归自己所有
- 希望第一版尽快上线，并能持续修改

### 3.2 核心任务

| 用户任务 | 平台能力 |
|---|---|
| 我不知道想法能不能做 | AI 澄清目标、用户、范围、可行性 |
| 我不知道产品应该有哪些页面 | 自动生成产品方案、页面结构和用户流程 |
| 我看不懂设计稿和代码 | 提供可点击原型、真实预览和业务验收清单 |
| 我不知道怎么买服务器和仓库 | 提供场景化购买与授权教程 |
| 我不会开发 | AI 自动生成代码、测试和修复 |
| 我不会部署 | 自动推送 Git、构建、部署和健康检查 |
| 以后想改功能怎么办 | 自然语言创建变更，自动生成新版本 |
| 改坏了怎么办 | 一键恢复上一发布版本 |

## 四、MVP 原则

1. **只问业务问题**。技术选择由平台完成。
2. **每个阶段有可见产出**。不能只显示一个长时间转圈。
3. **用户只在关键点确认**。产品方案、原型、预览验收、正式发布。
4. **默认安全**。生产部署前必须通过构建、测试和环境检测。
5. **基础设施归用户**。平台退出后用户仍拥有 Git、服务器和域名。
6. **版本不可变**。历史方案、原型、构建和发布必须可追溯。
7. **失败可恢复**。构建失败不污染线上版本，发布失败自动回滚。
8. **技术细节按需出现**。普通流程不显示 Git、SSH、Docker、日志和代码 diff。

## 五、MVP 主流程

| 阶段 | 用户看到的内容 | 平台产出 | 用户动作 | 进入下一阶段条件 |
|---|---|---|---|---|
| 想法 | AI 对话、参考资料、参考产品 | 结构化想法记录 | 描述目标和场景 | 信息足够生成方案 |
| 产品方案 | 一页产品说明 | 产品方案 V1、范围、验收标准 | 修改或确认 | 用户确认方案 |
| 原型 | 可点击网页原型 | 页面地图、用户流程、原型版本 | 点击体验并批注 | 用户确认原型 |
| 环境准备 | 购买和授权教程 | Git、服务器、域名连接状态 | 注册、购买、授权 | Git 和服务器检测通过 |
| 开发 | 业务化进度和预览地址 | 代码、分支、构建、测试报告 | 等待并按需处理业务选择 | 构建与自动测试通过 |
| 验收 | 验收清单和真实预览 | 构建版本、测试证据 | 实际操作并确认 | 用户验收通过 |
| 发布 | 发布确认和上线报告 | 发布标签、部署记录、线上版本 | 点击发布 | 健康检查通过 |
| 迭代 | 修改说明和影响范围 | 新变更、原型、构建和发布版本 | 确认原型与验收结果 | 新版本上线或回滚 |

环境准备可以与产品方案、原型和开发并行。用户没有服务器时仍可完成原型和预览，只是不能正式发布。

## 六、产品方案与原型设计

### 6.1 产品方案

产品方案是不可变版本，至少包含：

- 产品名称和一句话说明
- 目标用户
- 需要解决的问题
- MVP 核心使用流程
- 页面和功能清单
- 用户和权限模型
- 数据对象
- 验收标准
- 明确不做
- 预计开发时间
- 预计 AI 和服务器成本

产品方案每次确认产生新版本，例如 `P1`、`P2`。后续功能变更不能直接覆盖已确认版本。

### 6.2 原型

原型直接在浏览器中生成，不要求用户安装 Figma。

原型必须包含：

- 页面地图
- 完整用户流程
- 桌面端和移动端预览
- 使用模拟数据的可点击页面
- 页面批注和修改入口
- 桌面端、移动端截图
- 原型版本历史

原型状态：

`DRAFT -> READY -> APPROVED -> SUPERSEDED`

用户确认原型后，范围冻结。新增需求必须创建新的变更请求。

### 6.3 原型实现策略

MVP 使用可点击 Web 原型，不单独维护 Figma 源文件。

生成过程：

1. AI 根据产品方案生成页面和流程 JSON。
2. 原型渲染器生成静态前端和模拟数据。
3. 预览环境部署为独立只读版本。
4. 用户批注保存在 `prototype_comment`。
5. 修改后生成新的 `prototype_version`，旧版本只读保留。

原型页面和最终产品页面共享视觉规范和组件，但原型不连接真实数据库。

## 七、用户基础设施准备

### 7.1 环境资产

MVP 支持三类资产：

| 资产 | 是否必需 | MVP 方案 |
|---|---|---|
| Git 私有仓库 | 必需 | GitHub 优先，后续增加 Gitee |
| Ubuntu 服务器 | 正式发布必需 | 任意支持 SSH 的 Ubuntu 22.04/24.04 |
| 域名 | 可选 | 首版可先用服务器地址，后续增加域名向导 |

### 7.2 教程系统

教程不是独立 FAQ，而是嵌入当前步骤的可执行向导。

每个教程步骤包含：

- 这一步为什么需要
- 推荐购买哪个产品
- 推荐配置
- 预计价格
- 操作截图
- 需要复制或授权的字段
- 完成后的检测方法
- 常见错误和修复方式

MVP 首批教程：

- 创建 GitHub 私有仓库
- 为 Regent 授权仓库访问
- 购买腾讯云轻量服务器
- 购买阿里云 ECS
- 安装 Ubuntu 22.04/24.04
- 设置服务器安全组 22、80、443
- 添加 Regent 公钥

### 7.3 Git 授权

优先使用 Git 平台 OAuth 或 GitHub App，不让用户复制长期令牌。

如果 MVP 暂时只能使用令牌：

- 令牌只在服务端接收
- 使用现有配置密钥加密保存
- 页面只显示一次
- 日志、API 响应和错误信息不得回显
- 用户可以随时撤销并重新连接

### 7.4 服务器授权

平台为每台服务器生成独立 SSH 密钥对：

1. 浏览器显示公钥。
2. 教程指导用户把公钥加入云服务器。
3. 用户只填写服务器 IP 和 SSH 用户名。
4. 平台使用私钥连接，不接受长期保存 SSH 密码。
5. 连接成功后自动登记主机指纹。

### 7.5 环境检测

检测分两层：

**平台侧检测**

- 域名可访问
- Git 仓库存在且可推送
- SSH 可连接
- 操作系统版本符合要求
- CPU、内存和磁盘达到最低配置
- 22、80、443 端口状态正确
- sudo 权限可用

**目标机检测**

- Docker 和 Compose 可用
- 反向代理和证书工具可安装
- 持久化目录可写
- 磁盘空间足够
- 系统时间与 DNS 正常

检测失败必须给出：

- 失败步骤
- 业务化原因
- 可执行的修复操作
- “重新检测”按钮

## 八、开发、构建与发布

### 8.1 默认技术栈

MVP 不允许用户选择技术栈。平台根据产品类型自动选择一套稳定模板，技术选型由平台统一维护。

默认部署方式：

- 单台 Ubuntu 服务器
- Docker Compose
- 应用容器
- 单机数据库
- 反向代理
- 自动 HTTPS
- 持久化数据和定时备份

### 8.2 构建过程

一次变更的执行步骤：

1. 从当前线上版本创建变更分支。
2. AI 根据已确认原型生成代码。
3. 执行静态检查。
4. 执行构建。
5. 执行自动测试。
6. 生成预览环境。
7. AI 自检并修复。
8. 生成验收材料和测试摘要。
9. 用户验收。
10. 合并主分支并创建发布标签。
11. 部署到用户服务器。
12. 健康检查通过后切换为线上版本。

### 8.3 用户可见进度

用户只看到以下业务化状态：

- 正在准备产品方案
- 正在生成原型
- 正在检查运行环境
- 正在开发核心功能
- 正在测试主要流程
- 预览已准备好
- 正在发布
- 发布成功
- 发布失败，已恢复上一版本

默认不显示命令日志、代码 diff、Docker 输出和 Git 输出。高级诊断信息必须由用户主动展开。

## 九、版本与分支模型

### 9.1 用户可见版本

| 版本 | 示例 | 说明 |
|---|---|---|
| 产品方案版本 | `Brief V2` | 产品范围和验收标准 |
| 原型版本 | `Prototype V3` | 用户确认的可点击原型 |
| 构建版本 | `Build B12` | 一次开发、测试和预览结果 |
| 发布版本 | `v0.2.0` | 真正部署到线上且经过健康检查 |

### 9.2 Git 分支

MVP 不向用户展示分支树，内部固定使用：

- `main`：唯一稳定分支，始终对应最近一次已验收产品状态
- `change/<change-id>`：每个产品变更的短生命周期工作分支
- `hotfix/<issue-id>`：线上紧急修复分支
- `release/vX.Y.Z`：不可变发布标签

不做长期 `develop`、`staging`、`release` 分支。

### 9.3 发布规则

1. 开发只能在变更分支进行。
2. 预览环境只能部署变更分支。
3. 用户验收前不能合并到 `main`。
4. 只有合并后提交才能创建发布标签。
5. 生产服务器只部署发布标签。
6. 回滚时重新部署上一个健康发布标签。
7. 代码提交、分支合并和标签创建全部自动完成。

### 9.4 版本号

首版默认 `v0.1.0`。

- 修复问题：补丁版本递增，例如 `v0.1.1`
- 新增功能：小版本递增，例如 `v0.2.0`
- 大范围重构：由平台提出，用户确认后升级大版本

用户不需要理解语义化版本，只看到“当前线上版本”和“历史版本”。

### 10.3 聚合规则

- `Product` 是个人产品根聚合
- `ProductBriefVersion`、`PrototypeVersion`、`ProductRelease` 是不可变版本
- `ProductChange` 是独立聚合，只持产品、方案和原型的 ID
- `BuildVersion` 记录一次构建事实，不直接修改发布聚合
- `EnvironmentAsset` 只保存连接状态和密文引用，不保存明文凭据
- 跨聚合流转由应用服务显式编排

## 十一、核心状态机

### 11.1 产品生命周期

`DRAFT -> ACTIVE -> PAUSED -> ARCHIVED`

当前工作阶段单独保存：

`IDEA -> BRIEF -> PROTOTYPE -> BUILD -> ACCEPTANCE -> RELEASE -> LIVE`

产品和阶段分开，避免一个巨大状态机同时表示生命周期和当前步骤。

### 11.2 原型

`DRAFT -> READY -> APPROVED -> SUPERSEDED`

驳回或修改产生新原型版本，不原地修改已批准版本。

### 11.3 变更

`DRAFT -> PLANNED -> BUILDING -> PREVIEW_READY -> ACCEPTED -> RELEASED`

失败分支：

`BUILDING -> FAILED`
`PREVIEW_READY -> CHANGES_REQUESTED`
`ACCEPTED -> RELEASED` 只有发布健康检查通过后才能完成

### 11.4 构建

`QUEUED -> RUNNING -> TESTING -> SUCCEEDED`

异常状态：

`FAILED`、`CANCELLED`、`INTERRUPTED`

### 11.5 发布

`PREPARING -> DEPLOYING -> HEALTH_CHECK -> LIVE`

异常状态：

`FAILED`、`ROLLED_BACK`

## 十五、安全与信任

- Git 凭据和 SSH 私钥必须加密保存
- 不允许明文密码落库或进入日志
- 平台生成 SSH 密钥，用户只添加公钥
- 浏览器不显示私钥
- 生产部署前必须重新校验凭据
- 每次发布记录操作人、时间、构建、提交、标签和健康检查
- 用户可随时撤销 Git 和服务器授权
- 用户可导出产品方案、原型、发布历史和源代码
- 平台停止服务后，用户仍拥有 Git 仓库、服务器、域名和数据备份

## 十六、MVP 成功指标

- 非技术用户无需终端完成产品创建的转化率
- 从确认产品方案到首个可点击原型的时间
- 从确认原型到首个可验收预览的时间
- Git 连接完成率
- 服务器环境一次检测通过率
- 首次发布成功率
- 发布失败自动回滚成功率
- 用户验收一次通过率
- 7 天内从想法到上线产品的完成率

北极星指标：

> 7 天内完成从想法到首个线上 Web 产品，且无需人工研发介入的个人用户数。

## 十七、分阶段落地

### 阶段 0：设计和导航收敛

- 建新分支
- 提交本设计和删除清单
- 不直接改现有生产数据

### 阶段 1：新产品壳与数据骨架

- 新增 `studio` 上下文
- 新增 V75 及后续迁移
- 登录后进入“我的产品”
- 旧企业菜单从新路由下线

### 阶段 2：方案与原型闭环

- 想法澄清
- 产品方案版本
- 可点击原型
- 页面批注和原型确认

### 阶段 3：环境准备闭环

- Git 和服务器教程
- 连接向导
- 环境检测
- 自动基础配置

### 阶段 4：构建与预览闭环

- 内部复用 `execution`
- 构建版本和变更分支
- 自动测试
- 预览地址
- 业务验收清单

### 阶段 5：发布、回滚与迭代

- 发布标签
- 自动部署
- 健康检查
- 一键回滚
- 自然语言变更

### 阶段 6：旧代码与旧数据物理清理

- 删除旧前端页面和路由
- 删除旧消费者 API
- 迁移历史数据
- 停止旧表写入
- 在独立迁移窗口备份后删表

## 十八、V1.0.7 MVP 验收标准

必须完成以下端到端场景：

1. 新用户不安装 Codex，不打开终端。
2. 用户描述一个产品想法。
3. 平台生成产品方案和可点击原型。
4. 用户能够批注并确认原型。
5. 用户按教程创建 Git 仓库。
6. 用户按教程购买 Ubuntu 服务器。
7. 平台通过环境检测。
8. 平台自动创建变更分支并完成开发。
9. 平台自动推送代码、运行测试并生成预览。
10. 用户按验收清单完成验收。
11. 平台自动合并主分支、创建发布标签并部署。
12. 上线失败时自动恢复上一版本。
13. 用户提出一次自然语言修改并生成新版本。
14. 用户能够查看历史版本并恢复到上一版本。

只要以上任何一步仍然要求用户理解 Git、SSH、Docker、代码或部署脚本，MVP 就没有完成。
