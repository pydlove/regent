# 个人产品创造平台删除与迁移清单

> 分支：`feature_V1.0.7_R100B001`
> 适用范围：V1.0.7 个人产品 MVP
> 原则：先替换主路径，再冻结旧写入，备份后物理删除

## 一、处置分类

现有能力分四类处理：

| 分类 | 处理方式 |
|---|---|
| 新产品直接复用 | 保留代码和数据，换产品层调用 |
| 仅作为内部引擎 | 保留领域与执行能力，删除用户入口 |
| 历史兼容 | 保留只读数据和兼容代码，冻结写入 |
| 确认废弃 | 从新路由下线，随后删除代码和数据库表 |

不能为了“看起来干净”直接执行大范围 DROP TABLE。产品方案、原型、发布历史和用户资产必须先完成迁移与备份。

## 五、数据迁移步骤

### 第一步：新增结构

新增 V75 之后的迁移，只创建 `studio` 表，不修改旧表。

### 第二步：回填产品

每个未删除的 `project` 生成一个 `product`：

- `project.owner_id -> product.owner_id`
- `project.name -> product.name`
- 自动生成 slug
- 有历史发布的项目默认为 `ACTIVE`
- 无工作区且未使用的项目默认为 `DRAFT`

### 第三步：回填历史资产

- `deployment_server` 转为 `environment_asset(type=SERVER)`
- Git 配置转为 `environment_asset(type=GIT)`
- 用户附件保持原表，挂到对应产品
- 历史产品版本转为只读发布记录，不反向生成新构建

### 第四步：双读观察

- 新 UI 只读 `studio`
- 旧数据生成只读历史视图
- 记录所有仍访问旧表的调用

### 第五步：冻结旧写入

- 关闭旧 Controller
- 关闭旧定时任务
- 关闭旧事件消费
- 保证新系统不再产生旧表数据

### 第六步：备份与物理删除

- 完整 mysqldump
- 导出附件目录清单
- 在独立发布窗口执行删表迁移
- 验证新系统启动、登录、产品创建、构建、发布和回滚

## 六、兼容期策略

建议保留一个只读入口：

`/legacy/history`

只允许查看：

- 历史项目名称
- 历史版本号
- 历史发布记录
- 历史附件

不提供：

- 新建和编辑
- 成员和流程管理
- 重新触发旧研发流程
- 新任务派发

## 七、删除执行顺序

1. 上线新 `studio` 路由和产品首页
2. 删除旧导航与旧路由
3. 验证新闭环
4. 关闭旧 API
5. 删除旧前端页面和组件
6. 删除旧应用服务
7. 删除旧领域模型和测试
8. 冻结旧表写入
9. 备份
10. 物理删除旧表

第 1 到 3 步未验证前，不执行第 4 步以后操作。

## 八、禁止事项

- 禁止在同一个发布中同时重做 UI、迁移数据和 DROP 旧表
- 禁止直接删除用户 Git 仓库或服务器
- 禁止删除附件物理文件而未核对数据库引用
- 禁止把旧表数据直接覆盖为新产品版本
- 禁止让旧流程继续在后台定时运行
- 禁止保留无法维护的双写逻辑超过一个发布周期

## 九、完成标准

- 新用户只看到“我的产品”
- 旧企业研发菜单不可见
- 旧 API 不再被前端调用
- 新 `studio` 数据完整覆盖主流程
- 旧数据完成只读兼容或归档
- 所有用户资产仍归用户所有
- 删除旧代码后全量构建和端到端测试通过
