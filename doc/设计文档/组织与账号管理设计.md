# Regent 组织与账号管理设计

| 项目 | 内容 |
|---|---|
| 文档状态 | 第一版已实现，多组织全链路继续迭代 |
| 编写日期 | 2026-10-23 |
| 关联文档 | `ARCHITECTURE.md`、`TECH_STACK.md`、`研发交付全流程设计.md` |
| 设计目标 | 在账号和项目之间增加组织租户层，让管理员管理组织、成员、邀请和项目，同时保持现有账号与项目数据不丢失 |
| 不做什么 | 不做部门树、LDAP/SSO、复杂审批流、跨组织共享项目；这些能力放到后续阶段 |

## 一、结论先行

Regent 需要组织层，但必须把三个概念分开：

```text
账号（全局身份）
  → 组织成员（人在哪个组织、在组织里是什么角色）
    → 项目（项目属于组织）
      → 项目成员与项目角色（产品、技术、测试）
```

核心决策：

1. **账号全局唯一**。同一个账号可以加入多个组织，不需要为每个组织注册一套账号。
2. **组织是业务租户根**。项目必须归属于且只归属于一个组织。
3. **项目角色不上升为组织角色**。产品、技术、测试负责人仍然只在具体项目内有效。
4. **组织管理员负责账号生命周期，项目经理负责项目协作**。两者都可以进入组织管理，但可用动作不同。
5. **创建账号走邀请制**。管理员创建邀请，成员自己设置密码；系统不接受管理员长期掌握成员明文密码。
6. **组织管理员不默认获得项目敏感数据权限**。管理员可以管理组织与项目元数据，但项目代码、附件、SSH 凭据仍需项目成员身份。

## 二、角色模型

### 2.1 组织角色

| 角色 | 代码 | 说明 |
|---|---|---|
| 组织所有者 | `ORG_OWNER` | 组织最高负责人；可转移所有权，不能被普通管理员移除 |
| 组织管理员 | `ORG_ADMIN` | 管理组织信息、成员、邀请、项目和审计 |
| 项目经理 | `PROJECT_MANAGER` | 可查看组织成员和项目，创建/管理自己有权限的项目，安排项目成员 |
| 普通成员 | `ORG_MEMBER` | 只能访问被加入的项目 |

一个账号在一个组织内可以同时拥有多个组织角色。例如某人可以同时是 `ORG_ADMIN` 和 `PROJECT_MANAGER`。

### 2.2 与项目角色的关系

```text
组织角色：能不能进入组织管理、能不能创建账号
项目角色：能不能参与和推进某个项目
```

两者不得混用：

- `ORG_ADMIN` 不会自动成为所有项目的产品负责人或技术负责人。
- `PROJECT_MANAGER` 不会自动获得某个项目的审批权，仍需分配项目角色。
- 项目负责人 `OWNER` 仍然是项目级角色，不是组织所有者。

### 2.3 权限矩阵

| 操作 | 组织所有者 | 组织管理员 | 项目经理 | 普通成员 |
|---|---:|---:|---:|---:|
| 进入组织管理页 | 是 | 是 | 是 | 否 |
| 修改组织名称/描述 | 是 | 是 | 否 | 否 |
| 创建新组织 | 是 | 是 | 否 | 否 |
| 邀请新账号加入组织 | 是 | 是 | 否 | 否 |
| 启用/停用组织账号 | 是 | 是 | 否 | 否 |
| 修改组织角色 | 是 | 是 | 否 | 否 |
| 查看组织成员目录 | 是 | 是 | 是 | 否 |
| 创建项目 | 是 | 是 | 是 | 否 |
| 查看组织内全部项目元数据 | 是 | 是 | 是 | 否 |
| 查看项目代码/附件/凭据 | 需项目成员 | 需项目成员 | 需项目成员 | 需项目成员 |
| 分配项目成员 | 是 | 是 | 是 | 否 |
| 转移组织所有权 | 是 | 否 | 否 | 否 |

项目经理可以进入组织管理，但默认不能创建账号或修改组织级角色。若实际团队需要，给该账号追加 `ORG_ADMIN` 即可，不新增模糊角色。

## 三、关键流程

### 3.1 首次创建组织

```text
已登录用户
  → 创建组织
  → 输入组织名称、组织标识
  → 系统创建 organization
  → 创建 organization_member(ORG_OWNER)
  → 自动切换为当前组织
```

自助模式下，任何已登录账号都可以创建自己的第一个组织。是否允许继续创建更多组织由配置控制：

```text
regent.organization.self-service-create=true
```

关闭后，只有平台部署管理员或现有组织所有者可以创建组织。

### 3.2 邀请并创建账号

管理员不直接为成员设置长期密码，而是创建邀请：

```text
组织管理员
  → 成员与邀请
  → 邀请成员
  → 输入邮箱、组织角色
  → 系统生成一次性邀请链接
  → 成员打开链接
  → 设置显示名称与密码
  → 邮箱不存在：创建 app_user
  → 邮箱已存在：复用现有账号
  → 写入 organization_member
  → 邀请状态变为 ACCEPTED
```

邀请规则：

- 链接默认 7 天有效，只可使用一次。
- 数据库只保存令牌 SHA-256，不保存邀请明文令牌。
- 同一邮箱对同一组织只能有一个未过期邀请。
- 邀请被接受前，管理员可以撤销。
- 已注册账号接受邀请时，不修改原密码，只增加组织成员关系。
- 未注册邮箱在接受邀请时创建账号，并自动视为邮箱已验证。

组织管理页创建成功后展示可复制的邀请链接，邮件服务可用时同时发送邮件。邀请流程不允许管理员手填密码；
需要立即建号时使用下一节的一次性初始密码流程。

### 3.2.1 管理员手动创建账号

除邀请外，组织管理员可以直接创建账号：

```text
组织管理员
  → 创建账号
  → 输入邮箱、显示名称、组织角色
  → 系统生成一次性初始密码
  → 创建 app_user
  → 写入 organization_member
  → 管理员复制初始密码并交给成员
  → 成员首次登录必须修改密码
```

约束：

- 手动创建只适用于尚未注册的邮箱；已有账号应使用邀请或在成员目录中分配角色。
- 初始密码由系统生成，只在创建响应中返回一次，数据库只保存 PBKDF2 哈希。
- `app_user.must_change_password=1` 时，业务接口返回 `PASSWORD_CHANGE_REQUIRED`，只允许访问登录资料、登出和改密接口。
- 完成改密后清除标记，前端重新加载组织和项目上下文。

### 3.3 项目归属组织

```text
项目经理创建项目
  → 选择组织
  → 填写项目标识、名称、本机路径
  → 创建 project(organization_id)
  → 创建 project_member(OWNER)
```

规则：

- 项目创建后不能更换组织。
- 项目标识在组织内唯一，不同组织可以拥有同名项目标识。
- 现有项目在迁移时自动归入原项目负责人的默认组织。
- 项目经理只能把项目成员分配给本组织成员；外部协作者需要先加入组织，或后续单独设计 guest 机制。

### 3.4 切换组织

顶部栏增加组织选择器：

```text
当前组织：杭州研发中心 ▾
          ├─ 杭州研发中心
          ├─ 个人工作区
          └─ 创建组织
```

当前组织保存在本机，同时作为 API 的租户上下文：

```http
X-Organization-Id: 42
```

后端每次请求校验当前账号是否为该组织成员。切换组织后，项目、任务、研发流程、交付、环境、服务器等所有列表切换到新组织范围。

### 3.5 账号停用与组织移除

需要区分两件事：

- **移出组织**：保留全局账号，只让该账号失去当前组织访问权。
- **停用账号**：平台级操作，账号在所有组织都不能登录。第一版只开放“移出组织”，平台级停用留到平台管理后台。

组织管理员不能删除自己的最后一个 `ORG_OWNER` 角色，也不能把组织变成无人管理状态。

## 四、数据模型

### 4.1 核心表

```sql
CREATE TABLE organization (
    id          BIGINT       NOT NULL AUTO_INCREMENT,
    code        VARCHAR(64)  NOT NULL,
    name        VARCHAR(128) NOT NULL,
    description VARCHAR(512) DEFAULT NULL,
    status      VARCHAR(16)  NOT NULL DEFAULT 'ACTIVE',
    created_by  BIGINT       NOT NULL,
    created_at  DATETIME(3)  NOT NULL,
    updated_at  DATETIME(3)  NOT NULL,
    deleted     TINYINT(1)   NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    UNIQUE KEY uk_organization_code (code)
);

CREATE TABLE organization_member (
    id              BIGINT      NOT NULL AUTO_INCREMENT,
    organization_id BIGINT      NOT NULL,
    user_id         BIGINT      NOT NULL,
    role_code       VARCHAR(32) NOT NULL,
    status          VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
    joined_at       DATETIME(3) NOT NULL,
    created_at      DATETIME(3) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_org_member_role (organization_id, user_id, role_code),
    KEY idx_org_member_user (user_id, organization_id)
);

CREATE TABLE organization_invitation (
    id              BIGINT       NOT NULL AUTO_INCREMENT,
    organization_id BIGINT       NOT NULL,
    email           VARCHAR(255) NOT NULL,
    role_code       VARCHAR(32)  NOT NULL,
    token_hash      CHAR(64)     NOT NULL,
    status          VARCHAR(16)  NOT NULL DEFAULT 'PENDING',
    expires_at      DATETIME(3)  NOT NULL,
    accepted_at     DATETIME(3)  DEFAULT NULL,
    accepted_by     BIGINT       DEFAULT NULL,
    created_by      BIGINT       NOT NULL,
    created_at      DATETIME(3)  NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_org_invitation_token (token_hash),
    KEY idx_org_invitation_lookup (organization_id, email, status)
);
```

### 4.2 项目表变更

```sql
ALTER TABLE project
    ADD COLUMN organization_id BIGINT DEFAULT NULL AFTER id,
    ADD KEY idx_project_organization (organization_id, deleted);

-- 迁移完成后：
ALTER TABLE project
    MODIFY COLUMN organization_id BIGINT NOT NULL;

ALTER TABLE project
    DROP INDEX uk_project_code,
    ADD UNIQUE KEY uk_project_org_code (organization_id, code);
```

现有 `owner_id` 暂时保留，作为迁移期兼容字段。新逻辑以 `project_member(OWNER)` 表达项目负责人身份，后续版本再统一清理 `project.owner_id`。

### 4.3 审计表

```sql
CREATE TABLE organization_audit_log (
    id              BIGINT      NOT NULL AUTO_INCREMENT,
    organization_id BIGINT      NOT NULL,
    actor_id        BIGINT      NOT NULL,
    action          VARCHAR(64) NOT NULL,
    target_type     VARCHAR(32) NOT NULL,
    target_id       BIGINT      DEFAULT NULL,
    detail_json     JSON        DEFAULT NULL,
    created_at      DATETIME(3) NOT NULL,
    PRIMARY KEY (id),
    KEY idx_org_audit_time (organization_id, created_at)
);
```

至少记录：

- 组织创建与信息修改；
- 成员邀请、接受、撤销；
- 组织角色变更；
- 项目创建与组织归属变更尝试；
- 成员移出组织。

## 五、迁移方案

迁移必须兼容现有账号和项目，不要求用户重新注册。

### 5.1 历史数据

```text
for each app_user:
    创建默认组织 personal_{userId}
    名称使用“{displayName}的工作组织”
    创建 organization_member(ORG_OWNER)

for each project:
    organization_id = 原 owner 的默认组织
```

现有 `project_member` 数据保持不变。项目负责人同时拥有新组织的 `ORG_OWNER` 和项目的 `OWNER`。

### 5.2 新注册用户

```text
注册成功
  → 创建 app_user
  → 创建默认个人组织
  → 创建 ORG_OWNER 成员关系
  → 登录后默认进入个人组织
```

被邀请进入企业组织后，个人组织仍然保留，用户可以在组织选择器中切换。

### 5.3 Flyway

建议新增 `V53__organization.sql`，一次完成：

1. 创建三张组织表和审计表；
2. 为现有账号创建默认组织；
3. 写入组织所有者成员关系；
4. 为 `project` 增加 `organization_id` 并回填；
5. 调整项目标识唯一索引；
6. 增加必要外键与索引。

历史 `V` 脚本不修改。

## 六、接口设计

### 6.1 当前账号可见组织

```http
GET /api/organizations
```

返回当前账号加入的组织、自己的组织角色和项目数量。

### 6.2 创建与维护组织

```http
POST /api/organizations
PUT  /api/organizations/{id}
GET  /api/organizations/{id}
```

创建组织时当前账号自动成为 `ORG_OWNER`。

### 6.3 成员与邀请

```http
GET    /api/organizations/{id}/members
PATCH  /api/organizations/{id}/members/{userId}/roles
DELETE /api/organizations/{id}/members/{userId}

GET    /api/organizations/{id}/invitations
POST   /api/organizations/{id}/invitations
DELETE /api/organizations/{id}/invitations/{invitationId}
POST   /api/organizations/{id}/accounts

GET    /api/invitations/{token}
POST   /api/invitations/{token}/accept
```

`POST /api/organizations/{id}/invitations` 返回一次性邀请链接；重复邀请只刷新未过期邀请的令牌，不创建多条待处理记录。
`POST /api/organizations/{id}/accounts` 用于手动创建账号，响应只返回一次系统生成的初始密码。

### 6.4 项目

现有接口增加组织上下文：

```http
GET  /api/projects?organizationId=42
POST /api/projects
```

项目创建请求增加必填 `organizationId`。服务端校验：

- 当前账号是该组织成员；
- 当前账号具有 `ORG_ADMIN`、`ORG_OWNER` 或 `PROJECT_MANAGER`；
- 项目标识在组织内未被占用。

### 6.5 组织上下文

所有业务请求由 Web 客户端带：

```http
X-Organization-Id: 42
```

服务端在鉴权拦截器中校验成员关系。缺省时不猜测组织；除组织列表、邀请接受等公共接口外直接返回 `400`。

## 七、界面设计

### 7.1 顶部组织切换器

放在现有项目选择器左侧：

```text
[杭州研发中心 ▾]  [全部项目 ▾]  [+]
```

组织切换后：

- 清空项目选择；
- 重新加载项目、任务、研发流程和交付数据；
- 记住最近一次组织。

### 7.2 一级菜单

新增 `组织`，只对 `ORG_OWNER`、`ORG_ADMIN`、`PROJECT_MANAGER` 显示：

```text
工作区
  工作台
  任务
  交付
  项目
  组织
```

普通成员看不到该入口；即便手工输入 URL，后端也返回无权限。

### 7.3 组织管理页

```text
组织
├─ 概览
├─ 成员
├─ 邀请
├─ 项目
└─ 审计
```

概览：

- 组织名称、创建时间、组织所有者；
- 成员数、项目数、待接受邀请；
- 当前账号的组织角色；
- 创建组织、邀请成员快捷入口。

成员：

- 搜索姓名/邮箱；
- 显示组织角色和可访问项目数；
- 管理员可调整组织角色、移出组织；
- 项目经理只读，不显示修改按钮。

邀请：

- 显示邮箱、角色、状态、过期时间；
- 创建成功后弹出邀请链接；
- 管理员可复制、撤销。

项目：

- 显示组织内全部项目元数据；
- 创建项目；
- 进入项目时仍校验项目成员身份；
- 管理员可分配项目负责人，但敏感项目数据不因组织管理员身份自动开放。

### 7.4 邀请接受页

公开路由 `/invite/{token}`：

```text
你被邀请加入「杭州研发中心」
角色：项目经理
邮箱：name@example.com

[显示名称]
[设置密码]
[确认密码]
[接受邀请]
```

链接失效、已接受、邮箱已注册但登录账号不一致时给出明确提示。

## 八、安全与审计

1. 所有组织级接口在服务端校验组织角色，不能依赖前端隐藏按钮。
2. 邀请令牌只保存 SHA-256，链接离开创建响应后不能从数据库还原。
3. 邀请默认 7 天过期、单次使用，撤销后立即失效。
4. 组织管理员不能读取成员密码，不提供“查看密码”能力。
5. 组织管理员不能因为组织角色自动读取项目代码、附件、部署凭据和环境密钥。
6. 跨组织访问统一返回 404 或 403，不能泄露目标组织是否存在。
7. 所有权限变更写审计日志，至少保存操作人、目标、前后角色和时间。
8. 邀请创建接口按账号和组织限流，防止批量探测邮箱。

## 九、验收标准

### 数据迁移

- 现有每个项目迁移后都有 `organization_id`。
- 现有项目负责人自动成为默认组织 `ORG_OWNER`。
- 原项目成员、任务、需求、Bug、测试和部署数据不丢失。
- 同一账号迁移后仍能登录并看到原项目。

### 权限

- 普通成员看不到组织菜单，直接访问组织接口返回 403。
- 项目经理可以查看成员和项目，但创建邀请返回 403。
- 组织管理员可以邀请、调整角色、移出成员。
- 只有 `ORG_OWNER` 可以转移组织所有权。
- 组织管理员未被加入项目时，不能读取任务、附件、凭据和部署配置。

### 邀请

- 新邮箱接受邀请后创建账号并加入组织。
- 已注册邮箱接受邀请后复用账号，只增加组织成员关系。
- 过期、伪造、已接受、已撤销令牌均不可用。
- 同一邀请令牌不能成功使用两次。

### 多组织

- 一个账号可以加入多个组织。
- 切换组织后只能看到该组织的项目和数据。
- 组织 A 的项目标识与组织 B 的项目标识可以相同。
- 跨组织访问项目返回无权限，不能通过修改 URL 绕过。

## 十、实施阶段

### 阶段 1：组织底座

- `organization`、`organization_member`、组织角色；
- 默认组织迁移；
- 项目归属组织；
- 组织列表与组织切换；
- 组织级权限守卫。

### 阶段 2：组织管理页

- 组织概览、成员目录；
- 经理/管理员动作差异；
- 项目列表与创建项目接入组织；
- 审计日志。

### 阶段 3：邀请与账号创建

- 邀请表、令牌、接受页；
- 新账号创建与已有账号复用；
- 邀请撤销、过期与邮件发送。

### 阶段 4：平台管理

- 平台管理员后台；
- 组织冻结与恢复；
- 平台级账号停用；
- 批量导入、SSO、部门与配额。

第一阶段完成后，用户已经可以创建组织、切换组织和在组织内管理项目；第三阶段完成后，管理员才具备完整的“邀请并创建账号”闭环。

## 十一、第一版实现记录

当前已实现：

- `V53__organization.sql`：组织、组织成员、邀请、审计表；
- 历史账号自动生成个人组织，历史项目自动回填 `organization_id`；
- 创建组织、编辑组织、组织切换；
- 组织成员目录、角色添加/移除、移出成员；
- 组织邀请链接、已有账号登录后接受、新邮箱接受时创建账号；
- 管理员手动创建账号，系统下发一次性初始密码，首次登录强制修改；
- 项目创建绑定当前组织，项目标识在组织内唯一；
- 组织管理权限矩阵：所有者和组织管理员可管理账号，项目经理可查看成员并管理项目；
- 组织审计记录和邀请令牌 SHA-256 存储。

第一版边界：

- 邀请链接由管理员复制发送，邮件自动发送留到后续版本；
- `project.organization_id` 暂时保留可空，以兼容历史测试和直接 SQL 数据；应用创建的新项目必须带组织；
- 项目、组织和组织管理接口已经按组织校验；任务、Bug、测试、部署等历史接口的
  `X-Organization-Id` 全链路租户上下文留到下一阶段统一改造。当前顶部组织切换首先过滤项目和项目下拉；
- 组织所有权转移、平台管理员后台、SSO 和批量导入尚未实现。
