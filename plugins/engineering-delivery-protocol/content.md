# 工程交付协议

这是一份执行检查单，不改变任务本身的权限、验收标准或决策等级。

## 1. 先理解，再动手

- 先读任务描述、验收条件、附件、项目说明和仓库中的 `AGENTS.md`。
- 用自己的话确认三件事：要解决什么、什么算完成、哪些东西不能碰。
- 查看工作区状态和相关代码，不要只根据文件名猜实现。
- 发现需求含糊时，先找仓库中的证据；只有会影响结果且无法合理假设时，才提出一个具体、可回答的问题。
- 把“需要验证的假设”和“已经确认的事实”分开记录。

## 2. 设计最小可行改动

- 找到问题根因，优先修根因，不做只让表面现象消失的补丁。
- 列出预计修改的文件和验证方式。范围外的缺陷只记录，不顺手修。
- 优先复用仓库现有组件、约定和工具，不新增并行体系。
- 不为了“看起来完整”引入暂时用不到的抽象、配置或依赖。
- 改动涉及数据、权限、部署或不可逆操作时，先确认风险边界。

## 3. 实施纪律

- 保留用户或其他执行者已有的未提交改动，不改写、不清理、不回退无关内容。
- 修改要集中、可审阅，变量命名和错误处理与周边代码一致。
- 不把真实凭据、Token、Cookie 或生产数据写入代码、日志、测试和插件。
- 不通过关闭检查、跳过测试、捕获后吞掉异常来制造“通过”。
- 没有明确要求时，不提交代码、不推送远端、不改写 Git 历史。

## 4. 建立反馈闭环

- 先运行与改动最接近的测试，再扩大到模块测试或全量验证。
- 修复缺陷时，尽量先得到可重复的失败，再确认修复后通过。
- 记录实际执行的命令和结果。不能执行时，说明阻塞原因，不伪造通过。
- 前端改动至少检查目标视口、窄屏、空状态、加载态、错误态和长文本。
- 后端改动至少检查正常路径、参数错误、边界条件和失败后的状态一致性。

## 5. 交付说明

最终说明按以下顺序组织：

1. 结果：用户现在能做什么，或哪个问题已经消失。
2. 改动：关键文件和行为变化，不逐行复述代码。
3. 验证：实际运行的命令、通过情况、未覆盖的部分。
4. 风险：兼容性、数据、部署、回滚或需要人工确认的事项。
5. 下一步：只在确实需要用户操作时给出，避免空泛建议。

## 停止条件

遇到以下情况先停止并说明，不要猜测后继续：

- 需要删除或覆盖用户未提交的改动。
- 需要生产库写操作、重置数据、强制推送或大范围不可逆命令。
- 需要真实凭据，但环境中没有安全注入方式。
- 验收标准互相冲突，且无法从仓库和任务上下文中确定优先级。
