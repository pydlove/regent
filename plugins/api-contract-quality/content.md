# API 契约与错误处理

## 契约设计

- 对外只暴露接口层 DTO，不直接序列化领域对象或数据库行。
- 字段名表达业务含义，同一概念在不同接口中保持一致。
- 新增字段优先做成可选且向后兼容；删除、改名和改变类型必须有迁移方案。
- 列表接口明确排序、过滤和分页规则；大数据集不能无限返回。
- 时间使用明确时区语义，金额使用不会丢精度的类型，枚举新增值要考虑旧客户端。
- 幂等接口使用稳定的幂等键或自然唯一约束，避免重复请求生成重复数据。

## 请求校验

- 必填、长度、格式、范围和枚举值在入口尽早校验。
- 业务规则放在领域层，接口层只做传输格式和基础校验。
- 批量接口限制数量，避免一次请求拖垮数据库或执行器。
- 上传接口校验大小、类型和实际内容，不能只信文件扩展名。

## 错误响应

- 参数错误返回 400，未认证返回 401，无权限返回 403，不存在返回 404，冲突返回 409。
- 错误消息用简体中文说明“哪里不对”和“怎么改”，不回显密码、Token、SQL 或完整堆栈。
- 同一类错误使用稳定错误码或结构，前端不靠模糊字符串匹配。
- 未知异常统一兜底并记录关联日志 ID；对外只返回安全摘要。

## 执行者接口

- 认领、心跳、上报和完成任务的状态迁移必须幂等且有租约保护。
- 同一任务不能被多个执行者同时有效认领。
- 上报内容先校验再落库，失败不能留下半完成状态。
- 修改 Agent 契约属于跨端兼容变更，必须同时检查平台、外部执行者和文档。

## 测试

- 每个成功路径至少配一个失败路径测试。
- 覆盖空值、越界、重复提交、资源不存在、无权限和依赖失败。
- 校验 HTTP 状态、响应字段和错误消息，不只断言“抛异常”。
- 契约变化后运行类型检查、接口测试和构建；如无法运行，明确说明。
