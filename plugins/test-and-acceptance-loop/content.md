# 测试与验收闭环

## 1. 明确验收证据

开始前把验收条件转成可观察的结果，例如：

- 某个接口在给定输入下返回预期状态和数据。
- 某个页面在桌面和手机宽度下不溢出、可操作、状态正确。
- 某个缺陷的复现步骤不再失败。
- 迁移在全新库和已有数据的库上都能通过。

不能只以“代码看起来没问题”作为完成证据。

## 2. 先建立最快反馈

- 后端：先跑相关单元测试，再跑模块测试，最后按需要跑集成测试或全量构建。
- 前端：先跑类型检查和目标组件测试，再跑构建；有可运行界面时补实际交互检查。
- 缺陷修复：先得到能稳定复现的失败，再改代码，再确认同一路径通过。
- 不存在的测试：如果改动值得回归而代码库已有测试体系，补一个聚焦测试；不要给无测试体系的项目凭空搭一套。

## 3. 覆盖边界

正常路径之外至少考虑：

- 空值、空列表、零值、最大值、重复提交和并发冲突。
- 权限不足、资源不存在、依赖超时和外部服务失败。
- 长文本、超长文件名、窄屏、慢加载和错误重试。
- 数据库事务失败后是否残留半完成状态。
- 幂等操作重复执行是否安全。

## 4. 不制造假通过

- 不跳过失败测试来换取构建成功。
- 不把未执行的测试写成“已通过”。
- 不用 mock 数据代替真实集成验证后宣称端到端可用。
- 测试环境缺依赖时，明确写出“未运行”及原因。
- 修复偶发失败前先收集日志和复现条件，不靠重跑碰运气。

## 5. 交付验证记录

使用下面的格式：

```text
已通过：
- `命令或操作`：结果摘要

未运行：
- `命令`：缺少 MySQL / 浏览器 / 凭据等具体原因

人工检查：
- 桌面视口、手机视口、关键交互或数据状态
```

若发现与本任务无关的既有失败，单独列出，不把它混进本次改动，也不擅自修复。
