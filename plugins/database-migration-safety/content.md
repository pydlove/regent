# 数据库迁移安全

## 基本原则

- 已执行过的版本脚本永不修改；发现错误只能追加新的更高版本修正。
- 建表结构只有一个来源：迁移脚本。禁止手工改表、禁止 `ddl-auto` 自动建表。
- 迁移工具必须禁止 `clean`，生产环境不能存在一键清库能力。
- 测试使用独立 schema，绝不能指向开发库或生产库。
- 每个迁移都要考虑：全新库执行、已有数据升级、失败后如何恢复。

## 编写迁移

- 文件名和版本号连续、可排序，说明简短准确。
- 新增列优先允许 `NULL` 或有安全默认值，避免大表长时间锁表。
- 大表加索引、回填数据和修改列类型前评估锁表时间与磁盘空间。
- 字符集、排序规则、时间精度和现有表保持一致。
- 外键、唯一索引和级联行为要明确，避免删除主表时意外清掉审计数据。
- 数据回填拆成可重复执行、可分批次的小步骤；不要用一条超大 UPDATE 锁住全表。
- 不在迁移脚本中写真实密码、Token 或环境专属地址。

## 兼容发布

当应用滚动发布、新旧实例会短暂共存时，采用扩展再收缩：

1. 先新增兼容字段或表。
2. 发布能同时读写新旧结构的应用版本。
3. 回填并校验数据。
4. 确认旧实例全部下线后，再删除旧字段。

禁止在同一次发布中先删旧字段、再指望旧实例还能正常工作。

## 验证

- 在全新测试库执行全部迁移，确认从零可启动。
- 在已有测试数据上执行新增迁移，确认默认值和回填结果正确。
- 检查唯一约束、外键和索引是否真的创建成功。
- 运行相关持久化集成测试，确认领域对象往返没有丢字段。
- 记录实际执行的迁移版本和未运行项；数据库不可用时如实说明。

## 回滚思维

Flyway 社区版默认不做自动回滚，因此迁移设计必须尽量小、可补偿：

- 删除或重命名前先备份并保留回退窗口。
- 数据修正保留来源和审计字段。
- 准备人工回退 SQL 或前向修复脚本，但不要把它偷偷塞进历史迁移。
- 高风险迁移先在可恢复环境演练，再进入生产。
